# A0.2 — Semantic Dependency Audit

**Status**: AUDIT IN PROGRESS
**Date**: 2026-07-28
**Applies to**: A0 — Domain Model Review
**Principle**: `Usuario.IdTenant` desaparece del modelo. Toda dependencia debe reemplazarse por: `Usuario.Id` (identidad), `UsuarioTenant` (membership), `AuthenticationContext` (contexto ejecución), `Acceso` (autorización), `Rol.IdTenant` (scope del rol).

## 2. Análisis detallado de entidades críticas

### 2.1 IdenExt.IdTenant — INITIAL_CONTEXT

**Hipótesis**: "IdTenant de pertenencia de la identidad externa"

**Uso real**:
- `SP_ProvIden_BuscarUsuario` (L569): Busca IdenExt por `SubExterno + IdProvIden`. **NO usa IdTenant en el WHERE**. Retorna IdTenant como columna pero no filtra por él.
- `SP_ProvIden_VincularUsuario` (L515): Al vincular, recibe `@IdTenant` y lo almacena como contexto de vinculación.
- `SP_Auth_LoginExterno` (L1326-1373): Auto-link por email filtra `Usuarios.IdTenant = @IdTenant` (esto desaparece). Al crear IdenExt, almacena `@IdTenant` como contexto.
- `SP_Auth_RenovarTokenProveedor` (L1181-1182): Lee `IdenExt.IdTenant` para registrar auditoría en `AudIdenExt`.
- `IdenExt` tiene columna separada `UltimoTenant int NULL` con FK a Tenants — tracking explícito del último tenant usado.
- `IdenExtService.cs` (L229): `IdTenant: userResult.Value.IdTenant` — patrón que se rompe con identidad global.

**Conclusión**: `IdenExt.IdTenant` NO es pertenencia. Es **INITIAL_CONTEXT** — registra en qué tenant se vinculó originalmente la identidad externa. El tracking de pertenencia activa se hace mediante `UltimoTenant`. La búsqueda (`SP_ProvIden_BuscarUsuario`) funciona sin IdTenant.

**Decisión**: KEEP. No eliminarlo. La columna responde a "¿en qué tenant se vinculó este provider externo?" que es una pregunta legítima diferente de "¿a qué tenant pertenece este usuario?".

**Impacto de eliminar Usuario.IdTenant**: IdenExtService.cs línea 229 usa `userResult.Value.IdTenant` para crear IdenExt — debe cambiar a `AuthenticationContext.IdTenant` o `usuarioTenant.IdTenant`.

### 2.2 HistorialIdenExt.IdTenant — AUDIT_CONTEXT

**Uso real**:
- `SP_ProvIden_RegistrarAuditoria` recibe `@IdTenant` y lo almacena.
- No se filtra por IdTenant en búsquedas — es registro.
- FK duplicada: `FK_HistorialIdenExt_Tenant` y `FK_HistorialIdEx_Tenant` — ambas sobre IdTenant → Tenants.Id.

**Conclusión**: AUDIT_CONTEXT. Responde a "¿en qué tenant ocurrió este cambio de identidad externa?".

**Decisión**: KEEP. Incluso si el usuario cambia de tenant, el registro histórico conserva el tenant original.

### 2.3 AudIdenExt.IdTenant — AUDIT_CONTEXT

**Uso real**:
- `SP_ProvIden_RegistrarAuditoria` almacena `@IdTenant`.
- `SP_Dashboard_IdenExt` filtra por `AudIdenExt.IdTenant = @IdTenant` (KPIs).
- `SP_Auth_RenovarTokenProveedor` escribe `AudIdenExt.IdTenant = i.[IdTenant]` (desde IdenExt).

**Conclusión**: AUDIT_CONTEXT. Misma lógica que HistorialIdenExt.

**Decisión**: KEEP.

### 2.4 UsuariosPermisos.IdTenant — SCOPE (por determinar)

**Uso real**:
- `TR_UsuariosPermisos_ValidarTenant`: Valida `u.IdTenant <> i.IdTenant` — es decir, asegura que el permiso directo se asigna en el mismo tenant que el usuario. **Este trigger desaparece con identidad global**.
- `SP_Permisos_Usuario_Efectivos` (L682, 693): Filtra `UsuariosPermisos.IdTenant = @IdTenant`. Recibe @IdTenant del contexto, no de Usuario.
- Índices `UX_UsuariosPermisos_Activo_App` y `UX_UsuariosPermisos_Activo_Global` incluyen IdTenant.
- Con Modelo A (Acceso.IdUsuarioTenant?), los permisos directos deben seguir el mismo patrón para coherencia: `IdUsuarioTenant? NULL` = Platform Scope, `NOT NULL` = Tenant Scope.

**Pregunta**: ¿El permiso directo pertenece al UsuarioTenant o es autorización contextual?

**Respuesta**: Es autorización, exactamente como Acceso. Un permiso directo "Usuario X puede hacer Y en el contexto del Tenant Z" es semánticamente idéntico a un Acceso "Usuario X tiene rol R en App A en el contexto del Tenant Z". Ambos deben usar el mismo modelo.

**Decisión**: **MIGRAR** a `IdUsuarioTenant?`. Coherencia arquitectónica con Acceso. Mismas reglas: NULL = Platform Scope, NOT NULL = Tenant Scope, FK compuesta a UsuarioTenant.

### 2.5 MFA.IdTenant — EXECUTION_CONTEXT (revisar en A1)

**Uso real**:
- `SP_MFA_Validar` (L747): Filtra `MFA.IdTenant = @IdTenant`. Recibe @IdTenant del contexto de ejecución.
- MFA se configura antes del login (registro de dispositivo TOTP) y se valida durante el login.
- Un usuario global podría tener MFA en tenant A pero no en tenant B.

**Opción A**: Migrar a `IdUsuarioTenant?` — semánticamente correcto pero complejo: el MFA se configura antes de que exista UsuarioTenant (el registro de MFA ocurre post-login pero pre-JWT completo).
**Opción B**: Mantener EXECUTION_CONTEXT — el MFA pertenece al par (usuario, tenant). Si cambia de tenant, configura otro MFA.

**Decisión temporal**: **KEEP como EXECUTION_CONTEXT**. Revisar en A1 si el flujo de registro MFA justifica la migración.

### 2.6 Grupos + GruposUsuarios

**Grupos.IdTenant**: OWNERSHIP — el grupo pertenece a un tenant. **KEEP**.

**GruposUsuarios**: No tiene IdTenant propio. El trigger `TR_GruposUsuarios_ValidarTenant` valida `g.IdTenant <> u.IdTenant`.

**Problema**: Sin Usuario.IdTenant, el trigger no puede validar que usuario y grupo compartan tenant.

**Solución**: El trigger debe cambiar a:
```sql
WHERE g.IdTenant <> (SELECT ut.IdTenant FROM UsuarioTenant ut
                     WHERE ut.IdUsuario = u.Id AND ut.EsTenantPrincipal = 1)
```

**Decisión**: **CAMBIA** — reescribir trigger contra UsuarioTenant.

## 5. Triggers — qué reglas protegen y cómo reemplazarlas

### 5.1 TR_Accesos_ValidarTenant

```sql
IF EXISTS (SELECT 1 FROM inserted i JOIN dbo.Usuarios u ON i.IdUsuario = u.Id
           WHERE i.IdTenant <> u.IdTenant)
```

**Regla protegida**: Un Acceso debe tener el mismo tenant que el Usuario al que pertenece.

**¿Sigue siendo necesaria?**: NO — con Modelo A, la integridad se garantiza mediante:
- FK `Acceso.IdUsuario → Usuarios.Id` (Usuario existe)
- FK compuesta `(Acceso.IdUsuarioTenant, Acceso.IdUsuario) → UsuarioTenant(Id, IdUsuario)` (cuando IdUsuarioTenant NOT NULL)
- Cuando IdUsuarioTenant IS NULL (Platform Scope), no hay validación de tenant — el rol debe tener IdTenant NULL (validación en servicio)

**Decisión**: **ELIMINAR**. Reemplazar por FK compuesta + validación en servicio.

### 5.2 TR_UsuariosPermisos_ValidarTenant

```sql
IF EXISTS (SELECT 1 FROM inserted i JOIN dbo.Usuarios u ON u.Id = i.IdUsuario
           WHERE u.IdTenant <> i.IdTenant)
```

**Regla protegida**: Un permiso directo debe tener el mismo tenant que el Usuario.

**¿Sigue siendo necesaria?**: NO — mismo razonamiento que Acceso. Migrar a IdUsuarioTenant? con FK compuesta.

**Decisión**: **ELIMINAR**. Reemplazar por FK compuesta + validación en servicio.

### 5.3 TR_GruposUsuarios_ValidarTenant

```sql
IF EXISTS (SELECT 1 FROM inserted i JOIN dbo.Grupos g ON g.Id = i.IdGrupo
           JOIN dbo.Usuarios u ON u.Id = i.IdUsuario
           WHERE g.IdTenant <> u.IdTenant)
```

**Regla protegida**: Un usuario solo puede pertenecer a grupos de su mismo tenant.

**¿Sigue siendo necesaria?**: SÍ — la regla de negocio sigue vigente. Un usuario del tenant Abarrotes no puede estar en un grupo del tenant Vestuario.

**Nueva fuente de tenant**: UsuarioTenant principal del usuario.

**Decisión**: **REESCRIBIR** — cambiar `u.IdTenant` por `(SELECT IdTenant FROM UsuarioTenant WHERE IdUsuario = u.Id AND EsTenantPrincipal = 1)`.

### 5.4 TR_Usuarios_ValidarEsSistema

```sql
IF EXISTS (SELECT 1 FROM inserted i JOIN dbo.Tenants t ON t.Id = i.IdTenant
           WHERE i.EsSistema = 1 AND t.EsSistema = 0)
```

**Regla protegida**: Un usuario de sistema solo puede pertenecer al tenant de sistema.

**¿Sigue siendo necesaria?**: SÍ — la regla de negocio sigue vigente.

**Nueva fuente de tenant**: UsuarioTenant principal del usuario (EsTenantPrincipal = 1).

**Decisión**: **REESCRIBIR** — `JOIN UsuarioTenant ut ON ut.IdUsuario = i.Id JOIN Tenants t ON t.Id = ut.IdTenant WHERE i.EsSistema = 1 AND t.EsSistema = 0 AND ut.EsTenantPrincipal = 1`.

### 5.5 TR_Usuarios_Mod

```sql
IF UPDATE(Nombre) OR UPDATE(Apellido) OR UPDATE(IdEstado) OR UPDATE(Email) OR UPDATE(IdTenant)
  UPDATE u SET FecMod = SYSDATETIME() ...
```

**Regla protegida**: Actualizar FecMod cuando cambian campos sensibles del usuario.

**Cambio**: Quitar `OR UPDATE(IdTenant)` porque la columna desaparece.

**Decisión**: **MODIFICAR** — cambiar a `IF UPDATE(Nombre) OR UPDATE(Apellido) OR UPDATE(IdEstado) OR UPDATE(Email)`.

### 5.6 TR_RolesHerencia_ValidarTenant

```sql
WHERE (rh.IdTenant IS NOT NULL AND rh.IdTenant <> i.IdTenant)
   OR (rp.IdTenant IS NOT NULL AND rp.IdTenant <> i.IdTenant)
```

**Regla protegida**: Roles en herencia deben compartir el mismo IdTenant (o ser globales).

**¿Depende de Usuario.IdTenant?**: NO — valida contra Roles.IdTenant.

**Decisión**: **KEEP**. Sin cambios.
