## Part 1: Login without IdTenant — identificación global

### 1.1 Flujo general

```
POST /api/auth/login
{
    "nomUsuario": "claudio",   // o email
    "password": "***",
    "idApp": 1,                // requerido
    "idTenant": null           // opcional — este es el caso sin IdTenant
}
```

```
1. Buscar Usuario por NomUsuario (SIN filtro de tenant)
      │
      ▼
2. ¿Encontrado?
   ├── NO  → CredencialesInvalidas (misma respuesta siempre, sin enumerar)
   │
   └── SÍ  → Validar password
               │
               ▼
3. ¿Password válido?
   ├── NO  → CredencialesInvalidas + registrar IntentoAcceso
   │
   └── SÍ  → Resolver contexto (ver 1.2)
```

### 1.2 Resolución de contexto sin IdTenant

La resolución de contexto sigue este árbol de decisión:

```
3. ¿Usuario tiene Platform Scope para idApp?
   ├── SÍ → ¿Tiene también UsuarioTenant activos?
   │        ├── 0 → ✅ JWT con IdTenant = NULL (Platform Scope puro)
   │        └── N → ¿Debe usar Platform o Tenant? → Ver 1.3
   │
   └── NO → ¿Cuántos UsuarioTenant activos tiene?
            ├── 0 → ❌ SinAccesoApp (no tiene membresía ni platform)
            ├── 1 → ✅ JWT con IdTenant = único UsuarioTenant.IdTenant
            └── N → ⚠️ Devolver 428 MULTIPLE_TENANTS (ver 1.4)
```

### 1.3 Usuario con Platform + Tenant(s): ¿qué contexto gana?

**Regla**: Si el usuario tiene Platform Scope para la App, no se le puede exigir elegir un tenant. El comportamiento por defecto es:

```
Platform Scope + 0 UsuarioTenant  → JWT Platform (IdTenant=NULL)
Platform Scope + 1 UsuarioTenant  → JWT Platform (IdTenant=NULL)
Platform Scope + N UsuarioTenant  → JWT Platform (IdTenant=NULL)
```

El usuario puede cambiar de contexto después vía **context-switch** (POST /api/auth/context).

**Razón**: Platform Scope es un permiso explícitamente asignado. Un usuario con PLATFORM_ADMIN no debería tener que elegir un tenant para loguearse. Si quiere operar en un tenant específico, usa context-switch.

### 1.4 Usuario multi-tenant sin Platform Scope: HTTP 428

```
POST /api/auth/login
{ "nomUsuario": "claudio", "idTenant": null, "idApp": 1 }

Respuesta: HTTP 428 Precondition Required
{
    "error": "MULTIPLE_TENANTS",
    "message": "Se requiere seleccionar un tenant",
    "tenants": [
        { "idTenant": 7,  "codigo": "ABARROTES",  "nombre": "Abarrotes del Valle" },
        { "idTenant": 8,  "codigo": "VESTUARIO",  "nombre": "Vestuario Express" },
        { "idTenant": 9,  "codigo": "ELECTRON",   "nombre": "Electrónicos Globales" }
    ]
}
```

**Incluir solo tenants donde el usuario tenga al menos un Acceso activo para idApp.**

El cliente (Blazor) muestra un selector de tenant. Al seleccionar, envía el mismo login con `idTenant` incluido.

## Part 2: Login with IdTenant — membresía explícita

### 2.1 Flujo

```
POST /api/auth/login
{
    "nomUsuario": "claudio",
    "password": "***",
    "idApp": 1,
    "idTenant": 7              // explícito
}
```

```
1. Buscar Usuario por NomUsuario → U1 encontrado
2. Validar password → OK
3. Resolver UsuarioTenant:
   ¿Existe UsuarioTenant(U1, Tenant=7) activo?
   ├── NO  → SinAccesoApp (membership no existe, inactiva o finalizada)
   └── SÍ  → continuar
4. Resolver Acceso:
   ¿Existe Acceso para (UsuarioTenant, IdApp) activo?
   ├── NO  → SinAccesoApp (no tiene acceso a esta app en este tenant)
   └── SÍ  → continuar
5. Validar Rol:
   ¿Rol.IdTenant == UsuarioTenant.IdTenant (o Rol.IdTenant IS NULL para global)?
   ├── NO  → Error de configuración (no debería ocurrir con FK)
   └── SÍ  → continuar
6. MFA? → Según política del tenant
7. Emitir JWT { IdUsuario, IdTenant, IdApp, permisos[] }
```

### 2.2 Validación Rol ↔ Tenant

| Rol.IdTenant | Contexto IdTenant | ¿Válido? |
|-------------|-------------------|----------|
| NULL (global) | Cualquiera | ✅ El rol global aplica en cualquier tenant |
| = UsuarioTenant.IdTenant | Mismo tenant | ✅ Coincidencia exacta |
| ≠ UsuarioTenant.IdTenant | Otro tenant | ❌ INVÁLIDO — error de configuración |

**Validación en asignación** (no en login): Cuando se asigna un Acceso, el servicio debe validar:
```csharp
if (rol.IdTenant != null && rol.IdTenant != usuarioTenant.IdTenant)
    return Result.Failure("TENANT_MISMATCH", "Rol no pertenece al tenant del usuario");
```

## Part 3: Usuario multi-tenant

### 3.1 Definiciones

| Término | Definición |
|---------|-----------|
| **Usuario mono-tenant** | Tiene exactamente 1 UsuarioTenant activo |
| **Usuario multi-tenant** | Tiene 2+ UsuarioTenant activos |
| **Usuario platform** | Tiene al menos 1 Acceso Platform Scope (IdUsuarioTenant=NULL) |
| **Usuario híbrido** | Tiene Platform Scope + 1+ UsuarioTenant |

### 3.2 Selección inicial de tenant

```
¿Usuario tiene Platform Scope para la App?
├── SÍ → Login como Platform (IdTenant=NULL). 
│         Si necesita operar en un tenant → context-switch.
│
└── NO → ¿Cuántos UsuarioTenant activos con Acceso a la App?
         ├── 0 → SinAccesoApp
         ├── 1 → Login directo a ese tenant
         └── N → HTTP 428 MULTIPLE_TENANTS
```

### 3.3 Context-Switch (nuevo endpoint)

```
POST /api/auth/context
Authorization: Bearer <jwt_actual>
{
    "idTenant": 8          // tenant destino
}
```

**Validaciones**:
1. JWT actual es válido (cualquier contexto)
2. Usuario existe y está activo
3. UsuarioTenant(IdUsuario, IdTenant=8) existe y está activo
4. Acceso(UsuarioTenant, IdApp) existe y está activo
5. Emitir **nuevo JWT** con el nuevo contexto

**Respuesta**:
```json
{
    "jwt": "nuevo_jwt...",
    "refreshToken": "nuevo_refresh...",
    "sesion": { "id": "guid", ... }
}
```

**Casos**:
| Contexto actual | Contexto destino | ¿Válido? |
|----------------|------------------|----------|
| Platform (NULL) | Tenant 8 | ✅ |
| Tenant 7 | Platform (NULL) | ✅ (si tiene Platform Scope) |
| Tenant 7 | Tenant 8 | ✅ (si tiene membership en ambos) |
| Tenant 7 | Tenant 7 | ❌ (mismo contexto — idempotente, no emite nuevo JWT) |
| Tenant 7 | Tenant inexistente | ❌ |
| Tenant 7 | Tenant sin Acceso | ❌ |

**Regla**: El context-switch **siempre emite un nuevo JWT**. No hay mutación del JWT actual. El JWT anterior sigue siendo válido hasta su expiración natural (máximo 15 minutos por seguridad).

### 3.4 Casos límite multi-tenant

| Caso | Comportamiento |
|------|---------------|
| Tenant inactivo | UsuarioTenant.Activo=0 → no se puede seleccionar. Si no hay otros → SinAccesoApp |
| Tenant sin Acceso a la App | No aparece en la lista del HTTP 428. Si es el único → SinAccesoApp |
| Membership finalizada (FechaFin) | UsuarioTenant con FechaFin < hoy se trata como inactivo |
| Membership suspendida | IdEstado = Suspendido → no se puede seleccionar |
| Usuario pierde último UsuarioTenant | Si tiene Platform Scope → puede seguir operando. Si no → no puede obtener JWT |
| Todos los UsuarioTenant inactivos | SinAccesoApp (aunque tenga Platform Scope, este es independiente) |

## Part 4: Platform Scope

### 4.1 Definición formal

```
Acceso: { IdUsuario, IdUsuarioTenant=NULL, IdApp, IdRol }
Rol:    { Id, IdTenant=NULL, Codigo, Nombre }
```

Un Acceso es Platform Scope **si y solo si**:
- `Acceso.IdUsuarioTenant IS NULL`
- `Rol asociado tiene IdTenant IS NULL`

### 4.2 Combinaciones válidas

| ¿Platform Scope? | IdUsuarioTenant | Rol.IdTenant | ¿Válido? |
|-----------------|-----------------|-------------|----------|
| ✅ Platform | NULL | NULL | ✅ |
| ❌ Mixto | NULL | NOT NULL | ❌ — Rol tenant asignado como Platform |
| ❌ Mixto | NOT NULL | NULL | ✅ — Rol global asignado en contexto de tenant |
| ✅ Tenant | NOT NULL | = UsuarioTenant.IdTenant | ✅ |
| ❌ Mixto | NOT NULL | ≠ UsuarioTenant.IdTenant | ❌ — Rol de otro tenant |

### 4.3 Reglas de integridad

**Regla 1**: `Acceso.IdUsuarioTenant IS NULL` requiere `Rol.IdTenant IS NULL`.
- Se valida en `AccesoService.AsignarAccesoAsync` antes de guardar.
- No requiere trigger en BD (validación en capa de aplicación).
- Quien tenga permiso para asignar Accesos Platform debe ser explícitamente consciente.

**Regla 2**: Un usuario no necesita UsuarioTenant para tener Platform Scope.
- `SP_Auth_Login` debe soportar: buscar usuario, validar password, encontrar Acceso con IdUsuarioTenant=NULL.
- No hay JOIN con UsuarioTenant cuando se resuelve Platform Scope.

**Regla 3**: Platform Scope es por App, no global al sistema.
- Un usuario puede tener Platform Scope en PASSPLAT pero no en ABARROTES.
- `SP_Permisos_Usuario_Efectivos` recibe @IdUsuario + @IdApp + @IdTenant=NULL y filtra `Acceso.IdUsuarioTenant IS NULL`.

**Regla 4**: Roles globales predefinidos.

| Rol | Código | Propósito |
|-----|--------|-----------|
| PLATFORM_ADMIN | PLATFORM_ADMIN | Acceso total a la plataforma |
| PLATFORM_EDITOR | PLATFORM_EDITOR | Gestión de configuración global |
| PLATFORM_SUPERVISOR | PLATFORM_SUPERVISOR | Solo lectura de métricas globales |
| PLATFORM_CONSULTA | PLATFORM_CONSULTA | Consulta de datos no sensibles |

Estos roles tienen `IdTenant=NULL` y `Codigo` con prefijo `PLATFORM_`.

**Regla 5**: JWT Platform (IdTenant=NULL) contiene **solo** permisos Platform Scope.
- `Acceso.IdUsuarioTenant IS NULL` + `Rol.IdTenant IS NULL`.
- No incluye permisos de ningún tenant, aunque el usuario tenga UsuarioTenant.
- Para obtener permisos de tenant, el usuario debe usar context-switch.

**Regla 6**: JWT Tenant (IdTenant=T) contiene permisos **Platform + Tenant T**.
- `SP_Permisos_Usuario_Efectivos` unifica: Accesos con `IdUsuarioTenant=NULL` (Platform) + Accesos con `IdUsuarioTenant` al UsuarioTenant de T.

### 4.5 ¿Quién puede tener Platform Scope?

Solo usuarios explícitamente asignados por un administrador con permiso para asignar Platform Scope. No hay auto-asignación. El endpoint de asignación de Accesos debe verificar que quien asigna tenga Platform Scope + el permiso `ASIGNAR_PLATFORM_SCOPE`.

## Part 5: JWT — diseño del token

### 5.1 Principios

1. **Un JWT = un contexto**. No hay JWT multi-contexto ni claims que representen múltiples tenants.
2. **El JWT es contextual a (Usuario, Tenant, App)**. IdTenant puede ser NULL (Platform Scope).
3. **No hay mutación silenciosa**. Cambiar de tenant requiere un nuevo JWT vía context-switch.
4. **El JWT expira**. Tiempo de vida: 15-60 minutos (configurable por tenant/política).

### 5.2 Claims mínimos

```json
{
    "sub": "123",                          // Usuario.Id
    "name": "Claudio Becerra",
    "email": "claudio@example.com",
    "tenant_id": "7",                      // Puede ser null (Platform)
    "app_id": "1",                         // App.Id
    "tenant_codigo": "ABARROTES",          // Código del tenant (opcional)
    "app_codigo": "PASSPLAT",             // Código de la App
    "session_id": "guid-de-la-sesion",
    "permissions": ["USR_VER", "USR_EDIT", "ROL_ASIGNAR"],
    "iat": 1700000000,
    "exp": 1700003600,
    "iss": "passplat",
    "aud": "passplat-web"
}
```

### 5.3 Context-switch y JWT

```
Contexto actual: { IdUsuario=123, IdTenant=7, IdApp=1 }
     │
     ├── POST /api/auth/context { idTenant: 8 }
     │       │
     │       ▼
     │   Nuevo JWT: { ..., tenant_id: 8, session_id: "nuevo-guid" }
     │   JWT anterior sigue válido hasta exp (15 min máx)
     │
     ├── POST /api/auth/context { idTenant: null }  (Platform)
     │       │
     │       ▼
     │   Nuevo JWT: { ..., tenant_id: null, ... }
     │
     └── POST /api/auth/logout (revoca TODAS las sesiones del usuario)
```

### 5.4 Claims de permisos

Los permisos en el JWT corresponden al conjunto resuelto por `SP_Permisos_Usuario_Efectivos` para el contexto actual. No hay permisos acumulativos de múltiples tenants en un solo JWT.

**Regla**: Si un usuario tiene roles en Tenant A y Tenant B, el JWT en Tenant A solo contiene permisos de Tenant A (más Platform Scope si aplica).

## Part 6: Access Matrix — casos completos

### Notación

| Símbolo | Significado |
|---------|-------------|
| U(n) | Usuario con Id=n |
| UT(u,t) | UsuarioTenant: usuario u en tenant t |
| A(id) | Acceso |
| R_Tn(c) | Rol de tenant n con código c |
| R_P(c) | Rol platform con código c |
| ✅ | Combinación válida y esperada |
| ❌ | Combinación inválida |
| ⚠️ | Válido con advertencia o comportamiento especial |

### Caso 1: Usuario mono-tenant clásico

```
U(1), UT(1, TA=7), A: { U1, UT(1,7), App=1, R_T7(ADMIN) }
```

**Login**: `POST /login { nomUsuario: "claudio", idTenant: null, idApp: 1 }`
- Busca U1 global → encuentra
- 1 UT activo → selecciona TA=7 automáticamente
- Acceso ADMIN para App 1 → OK
- **JWT**: { IdUsuario:1, IdTenant:7, IdApp:1, permisos: [ADMIN] }

**Resultado**: ✅ Login exitoso. Sin necesidad de idTenant.

### Caso 2: Usuario multi-tenant sin Platform Scope

```
U(2), UT(2, TA=7), UT(2, TB=8)
A1: { U2, UT(2,7), App=1, R_T7(EDITOR) }
A2: { U2, UT(2,8), App=1, R_T8(CONSULTA) }
```

**Login sin idTenant**: HTTP 428 MULTIPLE_TENANTS → elige TB → `POST login { idTenant:8 }` → JWT con IdTenant=8, permisos CONSULTA.

**Login con idTenant**: OK.

**Resultado**: ✅ Login con selección de tenant.

### Caso 3: Platform Scope puro

```
U(3), 0 UsuarioTenant
A: { U3, NULL, App=1, R_P(PLATFORM_ADMIN) }
```

**Login sin idTenant**: 
- Busca U3 global → encuentra
- 0 UT → no hay membresía
- Platform Scope para App 1 → SÍ
- **JWT**: { IdUsuario:3, IdTenant:null, IdApp:1, permisos: [PLATFORM_ADMIN] }

**Resultado**: ✅ Login exitoso sin tenant.

### Caso 4: Platform + Tenant combinados

```
U(4), UT(4, TA=7)
A1: { U4, NULL, App=1, R_P(PLATFORM_SUPERVISOR) }
A2: { U4, UT(4,7), App=1, R_T7(EDITOR) }
```

**Login sin idTenant**: Tiene Platform Scope → JWT Platform (IdTenant=null). Permisos exclusivamente Platform: `[PLATFORM_SUPERVISOR]`. El tenant scope (EDITOR) NO se incluye en un JWT Platform.

**Login con idTenant=7**: JWT Tenant Scope con permisos EDITOR + PLATFORM_SUPERVISOR (roles globales aplican en cualquier contexto de tenant).

**Resultado**: ✅ Ambos flujos válidos. La regla es: **JWT Platform = solo permisos Platform. JWT Tenant = Platform + Tenant.**

### Caso 5: Usuario sin membresías, sin accesos

```
U(5), 0 UsuarioTenant, 0 Accesos
```

**Login**: Password válido, pero 0 UT y 0 Accesos Platform → SinAccesoApp.

**Resultado**: ❌ SinAccesoApp. Usuario existe en el sistema pero no tiene autorización para ninguna App.

### Caso 6: Platform Scope con rol de tenant (inválido)

```
U(6), 0 UsuarioTenant
A: { U6, NULL, App=1, R_T7(ADMIN) }   ← Rol.IdTenant = 7 (tenant)
```

**Estado**: ❌ INVÁLIDO. Error de asignación. `IdUsuarioTenant=NULL` requiere `Rol.IdTenant=NULL`.

**Asignación**: El servicio `AccesoService.AsignarAccesoAsync` rechaza esta combinación.

### Caso 7: Rol global en Tenant Scope (válido)

```
U(7), UT(7, TA=7)
A: { U7, UT(7,7), App=1, R_P(PLATFORM_CONSULTA) }
```

**Resultado**: ✅ Válido. Un rol global aplica en cualquier contexto de tenant. Permisos de PLATFORM_CONSULTA disponibles en TA=7.

### Caso 8: Membership suspendida

```
U(8), UT(8, TA=7, Estado=Suspendido)
A: { U8, UT(8,7), App=1, R_T7(VENDEDOR) }
```

**Login**: UsuarioTenant está suspendido → membership no activa → SinAccesoApp.

**¿Puede usar Platform Scope si tiene?**: No. Platform Scope requiere usuario activo. Si el usuario está suspendido globalmente (Usuario.IdEstado), no puede loguearse.

**Resultado**: ❌ SinAccesoApp.

### Caso 9: Membership finalizada

```
U(9), UT(9, TA=7, FechaFin='2026-06-01')
A: { U9, UT(9,7), App=1, R_T7(ADMIN) }
```

**Login (2026-07-28)**: FechaFin < hoy → membership expirada → SinAccesoApp.

**Resultado**: ❌ SinAccesoApp (membership expirada).

### Caso 10: Acceso revocado

```
U(10), UT(10, TA=7)
A: { U10, UT(10,7), App=1, R_T7(ADMIN), Activo=0 }
```

**Login**: UsuarioTenant activo, pero Acceso inactivo → SinAccesoApp.

**Resultado**: ❌ SinAccesoApp (el acceso fue revocado).

### Caso 11: App sin acceso para el usuario

```
U(11), UT(11, TA=7)
A: { U11, UT(11,7), App=2, R_T7(EDITOR) }  ← App 2, no App 1
```

**Login con idApp=1**: No hay Acceso para App 1 → SinAccesoApp.

**Login con idApp=2**: Hay Acceso → OK.

**Resultado**: ⚠️ SinAccesoApp para App 1, OK para App 2.

### Caso 12: Usuario sistema

```
U(SYS, EsSistema=1), UT(SYS, PLATFORM=0)
A: { SYS, NULL, App=1, R_P(PLATFORM_ADMIN) }
```

**Login**: Usuario sistema (EsSistema=1) sigue el flujo normal de autorización: AuthenticationContext → Acceso → Rol → Permisos. El Acceso Platform Scope con PLATFORM_ADMIN le concede explícitamente todos los permisos de plataforma. No hay bypass de autorización.

**Resultado**: ✅ Login exitoso vía Acceso + Rol, sin bypass.

### Caso 13: Usuario con membresía en tenant A pero intenta login en tenant B

```
U(13), UT(13, TA=7)
A: { U13, UT(13,7), App=1, R_T7(EDITOR) }
```

**Login con idTenant=8**: UsuarioTenant(13,8) no existe → SinAccesoApp.

**Resultado**: ❌ SinAccesoApp. El usuario no tiene membresía en tenant B.

### Caso 14: Denegación directa de permiso (UsuariosPermisos)

```
U(14), UT(14, TA=7)
A: { U14, UT(14,7), App=1, R_T7(ADMIN) }
UP: { U14, UT(14,7), P(456), IdTipoAsig=2 (denegar) }
```

**Login**: JWT con permisos ADMIN excepto P(456) que está denegado explícitamente.

**Resultado**: ✅ Login exitoso, permiso P(456) excluido.

### Caso 15: Platform + multi-tenant (híbrido complejo)

```
U(15), UT(15, TA=7), UT(15, TB=8)
A1: { U15, NULL, App=1, R_P(PLATFORM_ADMIN) }
A2: { U15, UT(15,7), App=1, R_T7(EDITOR) }
A3: { U15, UT(15,8), App=2, R_T8(CONSULTA) }
```

**Login App 1 sin idTenant**: Tiene Platform Scope → JWT Platform. Permisos exclusivamente Platform: `[PLATFORM_ADMIN]`. EDITOR no se incluye en JWT Platform.

**Login App 1 con idTenant=7**: JWT con IdTenant=7. Permisos: PLATFORM_ADMIN + EDITOR.

**Login App 1 con idTenant=8**: UsuarioTenant(15,8) no tiene Acceso a App 1 → SinAccesoApp.

**Login App 2 con idTenant=8**: JWT con IdTenant=8, App=2. Permisos: CONSULTA (Platform Scope no existe para App 2).

**Resultado**: ✅ Escenarios válidos según combinación.

### Caso 16: Usuario con múltiples roles en misma App+Tenant

```
U(16), UT(16, TA=7)
A1: { U16, UT(16,7), App=1, R_T7(EDITOR) }
A2: { U16, UT(16,7), App=1, R_T7(CONSULTA) }
```

**SP_Permisos_Usuario_Efectivos**: Retorna unión de permisos de EDITOR + CONSULTA. La CTE recursiva ya hace DISTINCT.

**Resultado**: ✅ Múltiples roles = unión de permisos.

### Caso 17: Usuario dado de baja (Usuario.Eliminado=1)

```
U(17, Eliminado=1)
```

**Login**: Usuario eliminado lógicamente → SinAccesoApp. (SP_Auth_Login tiene filtro `u.Eliminado = 0`).

**Resultado**: ❌ SinAccesoApp. Usuario eliminado no puede loguearse.

## Part 7: Matriz conceptual definitiva

```
                         ┌─────────────────────┐
                         │       Usuario       │
                         │    IdUsuario = U    │
                         └──────────┬──────────┘
                                    │
                     ┌──────────────┴──────────────┐
                     │                             │
                     ▼                             ▼
          ┌───────────────────┐         ┌────────────────────┐
          │ Platform Access   │         │ UsuarioTenant      │
          │ UT = NULL         │         │ U + Tenant         │
          └─────────┬─────────┘         └─────────┬──────────┘
                    │                             │
                    ▼                             ▼
             Rol.IdTenant=NULL          Acceso.IdUsuarioTenant
                    │                             │
                    │                             ▼
                    │                    Rol Tenant / Global
                    │
                    └─────────────┬───────────────┘
                                  │
                                  ▼
                       AuthenticationContext
                         U + Tenant + App
                                  │
                                  ▼
                              JWT
```

### Reglas de permisos por tipo de JWT

| Contexto JWT | Platform Scope | Tenant T | Tenant T2 |
|-------------|---------------|----------|-----------|
| IdTenant = NULL | ✅ | ❌ | ❌ |
| IdTenant = T | ✅ | ✅ | ❌ |
| IdTenant = T2 | ✅ | ❌ | ✅ |

### Nunca

| Situación | ¿Ocurre? | Explicación |
|-----------|---------|-------------|
| Tenant A permissions → JWT Tenant B | ❌ Nunca | Cada JWT representa un único contexto tenant |
| Platform JWT → permisos de Tenant A | ❌ Nunca | JWT con IdTenant=NULL solo contiene permisos Platform |
| JWT Platform → operaciones sobre un tenant | ❌ Nunca | Para operar en un tenant, usar context-switch |

### Regla: Platform Scope no crea membership

> **Platform Scope autoriza operaciones de plataforma, pero nunca crea ni implica membership sobre un Tenant.**

Un usuario con PLATFORM_ADMIN puede hacer context-switch al Tenant A **solo si** tiene UsuarioTenant activo en A. El Platform Scope por sí solo no concede acceso a ningún tenant.

| ¿Tiene Platform Scope? | ¿Tiene UsuarioTenant en T? | ¿Puede switch a T? |
|------------------------|---------------------------|-------------------|
| ✅ | ✅ | ✅ |
| ✅ | ❌ | ❌ |
| ❌ | ✅ | ✅ |
| ❌ | ❌ | ❌ |

## Part 8: Nota sobre UsuarioTenant.EsTenantPrincipal

> `UsuarioTenant.EsTenantPrincipal` **no debe convertirse en el mecanismo general para seleccionar el contexto de login.**

### ¿Para qué sirve EsTenantPrincipal?

| Propósito | ¿Aplica? |
|-----------|---------|
| Fallback técnico en background services | ✅ |
| Resolver tenant en procesos sin AuthenticationContext | ✅ |
| Procesos batch o jobs donde no hay sesión de usuario | ✅ |
| Login interactivo de usuario multi-tenant | ❌ |

### ¿Dónde NO debe usarse?

- **Login sin IdTenant para usuario multi-tenant**: No debe seleccionar automáticamente el EsTenantPrincipal. Debe devolver HTTP 428 con la lista de tenants.
- **Context-switch**: No debe redirigir al EsTenantPrincipal. Debe respetar el tenant solicitado.
- **Asignación de Accesos**: No debe asumir que el tenant principal es el contexto correcto para asignar un rol.

### ¿Dónde SÍ debe usarse?

- **PasswordExpirationBackgroundService**: Al recorrer usuarios, necesita un tenant para resolver políticas de password. Usa EsTenantPrincipal como fallback porque no hay sesión interactiva.
- **EmailBackgroundService**: Al enviar notificaciones automáticas, puede necesitar el tenant del usuario para resolver templates de email.
- **Procesos de purga/mantenimiento**: Necesitan un tenant para filtrar datos, pero no hay contexto de usuario.

### Regla

```
En procesos interactivos (login, context-switch, API calls autenticadas):
  → Usar el AuthenticationContext (IdTenant explícito en JWT)

En procesos background (jobs, servicios automáticos):
  → Puede usarse EsTenantPrincipal como fallback
  → Documentar explícitamente cuándo se usa
  → Preferir siempre pasar IdTenant como parámetro si está disponible
```

Esto evita que `EsTenantPrincipal` se convierta en un sustituto encubierto de `Usuario.IdTenant`.
