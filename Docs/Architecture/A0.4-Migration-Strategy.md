## 1. Estado actual → estado objetivo

### 1.1 Tablas afectadas

| Tabla | Estado actual | Estado objetivo | Tipo de cambio |
|-------|--------------|----------------|----------------|
| **Usuarios** | `IdTenant int NOT NULL` + FK a Tenants | Sin columna IdTenant | ELIMINAR columna + FK + índices |
| **Accesos** | `IdTenant int NOT NULL` + FK a Tenants | `IdUsuarioTenant int? NULL` + FK compuesta a UsuarioTenant | MIGRAR columna + FK |
| **UsuariosPermisos** | `IdTenant int NOT NULL` + FK a Tenants | `IdUsuarioTenant int? NULL` + FK compuesta a UsuarioTenant | MIGRAR columna + FK |
| **UsuarioTenant** | No existe | Nueva tabla con FK a Usuarios + Tenants + metadata | CREAR |

### 1.2 Columnas existentes reutilizables

| Columna actual | ¿Reutilizable? | Destino |
|---------------|---------------|---------|
| Usuarios.IdTenant | ❌ Se elimina | Los datos se migran a UsuarioTenant.IdTenant |
| Accesos.IdTenant | ❌ Se elimina | Reemplazada por Accesos.IdUsuarioTenant |
| UsuariosPermisos.IdTenant | ❌ Se elimina | Reemplazada por UsuariosPermisos.IdUsuarioTenant |

### 1.3 Columnas nuevas

| Tabla | Columna | Tipo | Propósito |
|-------|---------|------|-----------|
| UsuarioTenant | Id | int IDENTITY | PK |
| UsuarioTenant | IdUsuario | int NOT NULL | FK a Usuarios |
| UsuarioTenant | IdTenant | int NOT NULL | FK a Tenants |
| UsuarioTenant | IdEstado | tinyint NOT NULL | Estado de la membresía |
| UsuarioTenant | EsTenantPrincipal | bit NOT NULL DEFAULT 0 | Solo para background services |
| UsuarioTenant | FechaIngreso | datetime2 NOT NULL | Inicio de membresía |
| UsuarioTenant | FechaFin | datetime2 NULL | Fin de membresía |
| UsuarioTenant | InvitadoPor | int NULL | FK a Usuarios (quien invitó) |
| UsuarioTenant | Origen | varchar(50) NOT NULL | 'MIGRATION', 'MANUAL', 'OAUTH', 'INVITE' |
| UsuarioTenant | UltimoAcceso | datetime2 NULL | Último login en este tenant |
| UsuarioTenant | Activo | bit NOT NULL DEFAULT 1 | Soft delete/desactivación |
| Accesos | IdUsuarioTenant | int NULL | Reemplaza IdTenant. NULL = Platform Scope |
| UsuariosPermisos | IdUsuarioTenant | int NULL | Reemplaza IdTenant. NULL = Platform Scope |

### 1.4 Relaciones que cambian

| Relación actual | Nueva relación |
|----------------|---------------|
| `Usuarios.IdTenant → Tenants.Id` | **ELIMINADA** |
| `Accesos.IdTenant → Tenants.Id` | **ELIMINADA** |
| `UsuariosPermisos.IdTenant → Tenants.Id` | **ELIMINADA** |
| (nueva) `UsuarioTenant.IdUsuario → Usuarios.Id` | FK directa |
| (nueva) `UsuarioTenant.IdTenant → Tenants.Id` | FK directa |
| (nueva) `Accesos.IdUsuarioTenant → UsuarioTenant.Id` | FK (NULL = Platform Scope) |
| (nueva) `Accesos.IdUsuario → Usuarios.Id` | FK directa (se mantiene) |
| (nueva) FK compuesta: `(Accesos.IdUsuarioTenant, Accesos.IdUsuario) → UsuarioTenant(Id, IdUsuario)` | Solo se evalúa cuando IdUsuarioTenant NOT NULL |

### 1.5 Datos incompatibles

| Situación | ¿Existe? | Acción |
|-----------|---------|--------|
| Usuario con IdTenant = NULL | ❌ No (columna NOT NULL) | N/A |
| Acceso con IdTenant ≠ Usuario.IdTenant | ⚠️ Posible (sin FK, solo trigger) | Preflight debe detectar |
| Usuario sin UsuarioTenant equivalente | ⚠️ Posible (corrupto) | Preflight debe detectar |
| Usuario eliminado lógicamente (Eliminado=1) | ✅ Previsto | No migrar a UsuarioTenant |
| Rol con IdTenant=NULL vs NOT NULL | ✅ Previsto | Se mantiene igual |
| Accesos con Rol.IdTenant NULL (global) en contexto de tenant | ✅ Válido (Regla 7) | Se mantiene igual |

**Legacy columns post-migración**: A partir de MIGRATE, las columnas legacy (Usuarios.IdTenant, Accesos.IdTenant, UP.IdTenant) son **READ exclusivamente para compatibilidad y contingencia**. Ningún SP, trigger, servicio C# o migración futura debe escribir en ellas. La fuente primaria es el nuevo modelo (UsuarioTenant, Accesos.IdUsuarioTenant, UP.IdUsuarioTenant). Esta restricción se mantiene hasta CONTRACT.

## 2. Migración de Acceso

### 2.1 Estrategia

Cada fila de Accesos actual tiene `IdTenant int NOT NULL`. Con el Modelo A:

- `IdTenant` → `IdUsuarioTenant` (FK a UsuarioTenant)
- `IdUsuario` se mantiene (FK a Usuarios)
- `IdUsuarioTenant = NULL` = Platform Scope

### 2.2 Reglas de migración

| Acceso actual | IdTenant | Nuevo IdUsuarioTenant | ¿Platform? |
|--------------|----------|----------------------|------------|
| IdUsuario=U1, IdTenant=TA | TA | Id del UsuarioTenant(U1, TA) | ❌ Tenant Scope |
| IdUsuario=U1, IdTenant=TA, Rol.IdTenant=NULL | TA | Id del UsuarioTenant(U1, TA) | ❌ Tenant Scope (rol global) |
| IdUsuario=U1, IdTenant=NULL (imposible hoy) | — | — | No aplica (columna NOT NULL) |

**No existen Accesos Platform Scope en los datos actuales** porque `IdTenant` es NOT NULL. Todos los Accesos existentes son Tenant Scope y se migrarán con `IdUsuarioTenant NOT NULL`.

Los Platform Scope se crearán explícitamente después de la migración, asignando Accesos con `IdUsuarioTenant=NULL` a usuarios que deban tenerlos.

### 2.3 Validación NULL → Rol.IdTenant=NULL

Después de la migración, cualquier nuevo Acceso con `IdUsuarioTenant=NULL` debe validar que el Rol asociado tenga `IdTenant=NULL`. Esta validación se implementa en:

- `AccesoService.AsignarAccesoAsync` (capa aplicación)
- No se implementa índice filtrado: SQL Server no soporta subconsultas en filtros de índices. La validación es responsabilidad exclusiva de la capa aplicación.

### 2.4 Identificación de accesos actualmente ambiguos o inválidos

**Preflight debe detectar**:
1. Accesos donde `IdTenant ≠ Usuario.IdTenant` (violación de trigger, posiblemente datos corruptos)
2. Accesos donde `Rol.IdTenant ≠ Accesos.IdTenant` (rol de otro tenant asignado a este acceso)
3. Accesos donde el Usuario no existe (FK huérfana)
4. Accesos donde el Usuario está eliminado (Eliminado=1)

## 3. Migración de Rol

### 3.1 Roles globales

Los roles con `IdTenant=NULL` ya existen y **no cambian**. La migración debe:

- Verificar que existan los 4 roles platform predefinidos: `PLATFORM_ADMIN`, `PLATFORM_EDITOR`, `PLATFORM_SUPERVISOR`, `PLATFORM_CONSULTA`.
- Si no existen, crearlos como parte de la migración (seed de plataforma).
- Si existen pero tienen otro nombre/código, documentar el mapeo.

### 3.2 Roles tenant

Los roles con `IdTenant NOT NULL` **no cambian**. Siguen perteneciendo a su tenant.

### 3.3 Normalización de códigos PLATFORM_*

Criterio: los roles platform deben tener `Codigo` con prefijo `PLATFORM_` para distinguirlos claramente en listados y asignaciones.

| Código esperado | Nombre | IdTenant |
|----------------|--------|----------|
| PLATFORM_ADMIN | Administrador de Plataforma | NULL |
| PLATFORM_EDITOR | Editor de Plataforma | NULL |
| PLATFORM_SUPERVISOR | Supervisor de Plataforma | NULL |
| PLATFORM_CONSULTA | Consulta de Plataforma | NULL |

## 4. Migración de UsuarioTenant

### 4.1 Estrategia

Cada usuario activo (Eliminado=0) con `IdTenant` actual genera **exactamente 1** UsuarioTenant.

```sql
-- ESTRATEGIA — NO EJECUTAR
INSERT INTO UsuarioTenant (IdUsuario, IdTenant, IdEstado, EsTenantPrincipal,
                           Origen, FechaIngreso, Activo)
SELECT
    u.Id,
    u.IdTenant,
    u.IdEstado,
    1,                            -- EsTenantPrincipal = true (único tenant hoy)
    'MIGRATION',
    COALESCE(u.FecCrea, SYSDATETIME()),
    1
FROM Usuarios u
WHERE u.Eliminado = 0;
```

### 4.2 Estado activo/inactivo

| Usuario actual | UsuarioTenant resultante |
|---------------|-------------------------|
| Eliminado=0, IdEstado=Activo | Activo=1, IdEstado=Activo |
| Eliminado=0, IdEstado=Inactivo | Activo=1, IdEstado=Inactivo |
| Eliminado=0, IdEstado=Bloqueado | Activo=1, IdEstado=Bloqueado |
| Eliminado=0, IdEstado=Pendiente | Activo=1, IdEstado=Pendiente |
| Eliminado=1 | **No se migra** (usuario no tiene membresía activa) |

### 4.3 EsTenantPrincipal

Para usuarios actuales (mono-tenant): `EsTenantPrincipal = 1`.

Para futuros usuarios multi-tenant (post-migración): el primer UsuarioTenant creado tendrá `EsTenantPrincipal = 1`. Los siguientes se crearán con `EsTenantPrincipal = 0`.

**Después de la migración**, `EsTenantPrincipal` solo se usa en background services. No tiene efecto en login, context-switch ni autorización.

### 4.4 FechaFin

Se deja NULL para membresías sin fecha de término conocida. Si existen datos de expiración en el sistema actual, migrarlos.

### 4.5 Detección de memberships duplicadas o inconsistentes

**Preflight debe detectar**:
1. Usuarios con Eliminado=0 pero sin IdTenant válido (FK huérfana)
2. Usuarios con Eliminado=0 pero con IdTenant apuntando a un Tenant inactivo/inexistente
3. Usuarios duplicados (mismo NomUsuario en múltiples tenants) — con identidad global, el primer registro sobrevive, los demás deben revisarse
4. Usuarios que no existen (FK huérfana en Accesos/otras tablas)

## 5. Migración de permisos

### 5.1 Recalcular permisos efectivos

Después de migrar Accesos → IdUsuarioTenant, `SP_Permisos_Usuario_Efectivos` debe recalcularse para verificar que los resultados sean idénticos a los actuales.

Estrategia: ejecutar el SP actual y el nuevo SP (con JOIN a UsuarioTenant) en paralelo sobre una copia de BD y comparar resultados. Si difieren, investigar antes de cortar.

### 5.2 UsuariosPermisos

Migración: `IdTenant` → `IdUsuarioTenant` con el mismo UsuarioTenant que Accesos.

**Validación pre-migración obligatoria** (debe ejecutarse en Phase 1 y NO debe retornar filas):

```sql
-- Validación 1: UP con IdTenant ≠ Usuario.IdTenant
SELECT
    up.Id,
    up.IdUsuario,
    up.IdTenant,
    u.IdTenant AS UsuarioIdTenant
FROM UsuariosPermisos up
INNER JOIN Usuarios u ON u.Id = up.IdUsuario
WHERE up.IdTenant <> u.IdTenant;

-- Validación 2: UP con Usuario inexistente
SELECT up.*
FROM UsuariosPermisos up
LEFT JOIN Usuarios u ON u.Id = up.IdUsuario
WHERE u.Id IS NULL;
```

**Regla**: Si alguna de estas validaciones retorna filas, Phase 3 debe **abortar**. No intentar inferir el tenant correcto. Los datos deben revisarse manualmente.

```sql
-- ESTRATEGIA — SOLO EJECUTAR SI VALIDACIONES PASAN
UPDATE up
SET up.IdUsuarioTenant = ut.Id
FROM UsuariosPermisos up
JOIN UsuarioTenant ut ON ut.IdUsuario = up.IdUsuario AND ut.IdTenant = up.IdTenant;
```

**Posmigración**: Los UsuariosPermisos con `IdUsuarioTenant=NULL` representan permisos Platform Scope (misma semántica que Acceso).

### 5.3 Preservar denegaciones explícitas

Las denegaciones (`IdTipoAsig = 2`) se migran igual que las concesiones. El campo `IdTipoAsig` no cambia de semántica.

### 5.4 Validar precedencia Deny > Allow

La regla actual de `SP_Permisos_Usuario_Efectivos` ya implementa Deny > Allow mediante:
```sql
WHERE NOT EXISTS (SELECT 1 FROM PermisosUsuarioDenegados pud WHERE pud.IdPermiso = pb.IdPermiso)
```

Esta regla **no cambia**. Solo se actualiza la fuente del IdTenant en el SP.

## 6. Migración de autenticación

### 6.1 SP_Auth_Login

**Cambio principal**: La búsqueda del usuario ya no filtra por `Usuarios.IdTenant = @IdTenant`.

```
Actual:   Buscar Usuario WHERE NomUsuario = @NomUsuario AND IdTenant = @IdTenant
Futuro:   Buscar Usuario WHERE NomUsuario = @NomUsuario  (global)
          ↓
          Resolver UsuarioTenant después de validar password
```

**Flujo futuro en SP**:
1. `@IdTenant` sigue siendo parámetro (compatibilidad)
2. Buscar Usuario por NomUsuario (sin tenant)
3. Si `@IdTenant IS NOT NULL`: validar UsuarioTenant existe
4. El SP **nunca** decide HTTP 428. Retorna un código de resultado indicando el estado de resolución (`SUCCESS`, `INVALID_CREDENTIALS`, `NO_ACCESS`, `MULTIPLE_TENANTS`, `PLATFORM_CONTEXT`). La capa Application/API transforma estos códigos en HTTP (428, 401, 403, etc.)
5. El resto del SP no cambia (validación password, MFA, sesión, etc.)

### 6.2 SP_Permisos_Usuario_Efectivos

**Cambio principal**: Reemplazar `Accesos.IdTenant = @IdTenant` por JOIN a UsuarioTenant.

```
Actual:   WHERE Accesos.IdTenant = @IdTenant
Futuro:   WHERE (Accesos.IdUsuarioTenant IS NULL AND Roles.IdTenant IS NULL)  -- Platform
          OR (Accesos.IdUsuarioTenant IN (SELECT Id FROM UsuarioTenant
               WHERE IdUsuario = @IdUsuario AND IdTenant = @IdTenant AND Activo = 1))  -- Tenant
```

### 6.3 Resolución Platform/Tenant

El nuevo flujo en servicios C#:

```
AuthenticationContext.IdTenant
    │
    ├── NULL → SP_Permisos recibe @IdTenant=NULL → solo Accesos Platform Scope
    │
    └── T    → SP_Permisos recibe @IdTenant=T → Platform + Tenant T
```

### 6.4 428 MULTIPLE_TENANTS

Implementación en AuthService (capa aplicación, no en SP):

```csharp
if (idTenant == null)
{
    var tenantsActivos = await _uow.GetCustomRepository<IUsuarioTenantRepository>()
        .ObtenerActivosConAccesoAsync(usuario.Id, idApp, ct);
    
    if (tenantsActivos.Count == 0)
    {
        // ¿Tiene Platform Scope?
        if (tienePlatformScope)
            return JWT Platform;
        else
            return SinAccesoApp;
    }
    
    if (tenantsActivos.Count == 1)
        idTenant = tenantsActivos[0].IdTenant; // Único, usar automáticamente
    else
        return HTTP 428 MULTIPLE_TENANTS;
}
```

### 6.5 Context-switch

Nuevo endpoint, no requiere migración de datos. Se implementa después de la migración (Fase 6-8).

## 7. Compatibilidad

### 7.1 Código existente que asuma Usuario.IdTenant

**16 puntos de falla** identificados en A0.2:

| Patrón | Ocurrencias | Estrategia de reemplazo |
|--------|-------------|------------------------|
| `idTenant ?? usuario.IdTenant` | 9 | Reemplazar por `idTenant ?? usuarioTenantPrincipal.IdTenant`. Si no hay AuthenticationContext disponible, usar UsuarioTenantRepository.ObtenerPrincipalAsync(usuario.Id) |
| `usuario.IdTenant` directo | 7 | Reemplazar por `usuarioTenant.IdTenant` desde UsuarioTenant resuelto explícitamente |

**Regla**: El `idTenant ?? usuario.IdTenant` se reemplaza por:
- Si hay `AuthenticationContext`: usar `authenticationContext.IdTenant` (nunca fallback)
- Si es un proceso interactivo: el IdTenant viene del JWT/request
- Si es un background service: usar `usuarioTenantPrincipal.IdTenant` con `EsTenantPrincipal = 1`

### 7.2 Servicios que usen EsTenantPrincipal

| Servicio | Uso actual | Reemplazo |
|----------|-----------|-----------|
| PasswordExpirationBackgroundService | `usuario.IdTenant` para política | UsuarioTenant con EsTenantPrincipal=1 |
| EmailBackgroundService | `log.IdTenant` | Ya usa log.IdTenant (KEEP) |
| IdenExtTokensRotacionJob | `idenExt.IdTenant` | Ya usa IdenExt.IdTenant (KEEP) |

### 7.3 Endpoints que necesiten AuthenticationContext

Todos los endpoints autenticados ya reciben el contexto del JWT. No hay cambios en la interfaz de los endpoints. El cambio es interno: cómo se resuelve el IdTenant dentro de los servicios.

### 7.4 Jobs/background services

| Job | Dependencia de Usuario.IdTenant | Reemplazo |
|-----|-------------------------------|-----------|
| PasswordExpirationBackgroundService | ALTA | UsuarioTenant principal |
| EmailBackgroundService | NINGUNA | KEEP |
| IdenExtTokensRotacionJob | NINGUNA | KEEP |
| Maintenance/Purge | NINGUNA | KEEP |

## 8. Integridad y seguridad

### 8.1 FKs

| FK actual | Acción | Nueva FK |
|-----------|--------|----------|
| FK_Usuarios_Tenant | ELIMINAR | — |
| FK_Accesos_Tenant | ELIMINAR | FK_Accesos_UsuarioTenant (IdUsuarioTenant → UsuarioTenant.Id) + FK compuesta |
| FK_UsuariosPermisos_Tenant | ELIMINAR | FK_UP_UsuarioTenant (IdUsuarioTenant → UsuarioTenant.Id) + FK compuesta |
| FK_Accesos_Usuario (IdUsuario → Usuarios.Id) | KEEP | Sin cambios |
| FK_UP_Usuario (IdUsuario → Usuarios.Id) | KEEP | Sin cambios |

### 8.2 Índices

| Índice actual | Acción | Nuevo índice |
|--------------|--------|-------------|
| UX_Usuarios_Tenant_NomUsuario | ELIMINAR | UX_Usuarios_NomUsuario (global) |

### 8.3 Unicidad

| Unicidad actual | Nueva unicidad |
|----------------|---------------|
| UNIQUE(IdTenant, NomUsuario) WHERE Eliminado=0 | UNIQUE(NomUsuario) WHERE Eliminado=0 — global |
| UNIQUE(IdTenant, Email) WHERE Eliminado=0 AND Email NOT NULL | UNIQUE(Email) WHERE Eliminado=0 AND Email NOT NULL — global |
| UNIQUE(IdUsuarioTenant, IdApp, IdRol) | Nueva — evita duplicados de Acceso en el mismo scope |
| — | **UX_UsuarioTenant_Usuario_Tenant**: UNIQUE(IdUsuario, IdTenant) — garantiza que una combinación usuario+tenant solo existe una vez. Esto no reemplaza el preflight (detección preventiva), sino que impide que duplicados vuelvan a ocurrir post-migración |

### 8.4 Validaciones de aplicación

| Validación | Dónde se implementa |
|-----------|-------------------|
| IdUsuarioTenant=NULL requiere Rol.IdTenant=NULL | AccesoService.AsignarAccesoAsync |
| IdUsuarioTenant NOT NULL requiere UsuarioTenant activo | AccesoService.AsignarAccesoAsync |
| IdUsuarioTenant NOT NULL requiere Rol.IdTenant = UsuarioTenant.IdTenant (o NULL) | AccesoService.AsignarAccesoAsync |
| Unicidad de NomUsuario global | UsuarioService.CrearAsync |
| Unicidad de Email global | UsuarioService.CrearAsync |

### 8.5 Detección de registros huérfanos (Preflight)

| Query de detección | ¿Qué detecta? |
|-------------------|---------------|
| Usuarios con Eliminado=0 pero sin UsuarioTenant post-migración | Error de migración |
| Accesos sin Usuario correspondiente | FK huérfana pre-existente |
| Accesos con IdTenant ≠ Usuario.IdTenant | Violación de trigger actual |
| Accesos con Rol de otro tenant | Error de configuración |
| UsuariosPermisos con Usuario inexistente | FK huérfana |

### 8.6 Prevención de asignaciones Platform inválidas

Después de la migración, la validación en `AccesoService.AsignarAccesoAsync` debe ser:

```csharp
if (dto.IdUsuarioTenant == null)
{
    // Platform Scope
    var rol = await _rolRepo.GetByIdAsync(dto.IdRol);
    if (rol.IsFailure || rol.Value.IdTenant != null)
        return Result.Failure("PLATFORM_ROLE_MISMATCH",
            "Platform Scope requiere un rol global (IdTenant=NULL)");
}
```

## 9. Migración por fases

### Phase 0 — Backup / snapshot

**Duración**: 1 hora
**Riesgo**: Ninguno (solo backup)

| Paso | Descripción |
|------|-------------|
| 0.1 | Backup completo de BD (diferencial + log) |
| 0.2 | Snapshot del código fuente (tag git: `pre-migration-a0`) |
| 0.3 | Exportar datos críticos a tablas de auditoría (Usuarios, Accesos, UsuariosPermisos) |

**Rollback**: Restaurar backup.

### Phase 1 — Preflight / auditoría (READ-ONLY)

**Duración**: 2-4 horas
**Riesgo**: Ninguno (solo lecturas)

| Paso | Descripción | Query de detección |
|------|-------------|-------------------|
| 1.1 | Detectar usuarios con Eliminado=0 pero con IdTenant inválido | `SELECT * FROM Usuarios WHERE Eliminado=0 AND IdTenant NOT IN (SELECT Id FROM Tenants)` |
| 1.2 | Detectar Accesos con IdTenant ≠ Usuario.IdTenant | `SELECT a.* FROM Accesos a JOIN Usuarios u ON a.IdUsuario = u.Id WHERE a.IdTenant <> u.IdTenant` |
| 1.3 | Detectar Accesos con Rol.IdTenant ≠ Accesos.IdTenant | `SELECT a.* FROM Accesos a JOIN Roles r ON a.IdRol = r.Id WHERE r.IdTenant IS NOT NULL AND r.IdTenant <> a.IdTenant` |
| 1.4 | Detectar UsuariosPermisos con IdTenant ≠ Usuario.IdTenant | Igual que 1.2 pero para UP |
| 1.5 | Detectar usuarios con NomUsuario duplicado global | `SELECT NomUsuario, COUNT(*) FROM Usuarios WHERE Eliminado=0 GROUP BY NomUsuario HAVING COUNT(*) > 1` |
| 1.6 | Detectar usuarios con Email duplicado global | `SELECT Email, COUNT(*) FROM Usuarios WHERE Eliminado=0 AND Email IS NOT NULL GROUP BY Email HAVING COUNT(*) > 1` |
| 1.7 | Detectar roles sin IdTenant (posibles platform roles) | `SELECT * FROM Roles WHERE IdTenant IS NULL` |
| 1.8 | Detectar Accesos con Platform Scope potencial (Rol.IdTenant=NULL) | `SELECT a.* FROM Accesos a JOIN Roles r ON a.IdRol = r.Id WHERE r.IdTenant IS NULL` |
| 1.9 | Generar informe de inconsistencias | Reporte consolidado |
| 1.10 | Detectar Accesos y UsuariosPermisos asociados a usuarios eliminados | `SELECT a.* FROM Accesos a INNER JOIN Usuarios u ON u.Id = a.IdUsuario WHERE u.Eliminado = 1` — misma query para UsuariosPermisos |

**Criterio de abortar**: Si 1.2, 1.5, 1.6 o 1.10 retornan filas, **NO continuar**. Revisar manualmente antes de Phase 2. Los datos corruptos o inconsistentes no deben migrarse automáticamente.

### Phase 2 — Schema migration

**Duración**: 1-2 horas
**Riesgo**: ALTO (modifica estructura)

| Paso | Descripción | Rollback |
|------|-------------|----------|
| 2.1 | CREAR tabla UsuarioTenant con FKs, índices, defaults | DROP TABLE |
| 2.2 | AGREGAR columna Accesos.IdUsuarioTenant (nullable) | ALTER DROP COLUMN |
| 2.3 | AGREGAR columna UsuariosPermisos.IdUsuarioTenant (nullable) | ALTER DROP COLUMN |
| 2.4 | CREAR índices temporales en nuevas columnas | DROP INDEX |
| 2.5 | CREAR FK compuesta (IdUsuarioTenant, IdUsuario) → UsuarioTenant(Id, IdUsuario) | ALTER DROP FK |

**Punto de restauración**: Si falla 2.1-2.5, rollback completo (Phase 0).

### Phase 3 — Data migration

**Duración**: 2-4 horas
**Riesgo**: ALTO (modifica datos)

| Paso | Descripción | Rollback |
|------|-------------|----------|
| 3.1 | INSERT UsuarioTenant desde Usuarios activos | DELETE FROM UsuarioTenant |
| 3.2 | Validar: COUNT(UsuarioTenant) = COUNT(Usuarios WHERE Eliminado=0) | Revisar y corregir |
| 3.3 | UPDATE Accesos.IdUsuarioTenant desde UsuarioTenant | UPDATE SET NULL (datos preservados en IdTenant original) |
| 3.4 | Validar: todos los Accesos tienen IdUsuarioTenant poblado | Revisar |

## 10. Rollback

### 10.1 Qué puede revertirse

| Fase | Reversible | Método |
|------|-----------|--------|
| Phase 0-1 | ✅ | No hay cambios |
| Phase 2 | ✅ | DROP TABLE UsuarioTenant, ALTER DROP COLUMN nuevas |
| Phase 3 | ✅ | DELETE UsuarioTenant, UPDATE Accesos/UP SET IdUsuarioTenant=NULL |
| Phase 4 | ✅ | Restaurar roles desde backup |
| Phase 5 | ⚠️ Parcial | Restaurar SPs/triggers desde backup. Los datos nuevos (UsuarioTenant) se mantienen |
| Phase 6 | ✅ | git revert. Build anterior sigue funcionando con BD actualizada |
| Phase 7 | ✅ | No hay cambios |
| Phase 8 | ✅ | Restaurar backup completo |

### 10.2 Qué no puede revertirse automáticamente

| Situación | Por qué | Solución |
|-----------|---------|----------|
| Usuarios con NomUsuario duplicado después de migración | Dos usuarios de distintos tenants tenían el mismo NomUsuario. Con unicidad global, el segundo no es válido | Detectar en Preflight (Phase 1.5). Resolver manualmente antes de migrar |
| Usuarios con Email duplicado después de migración | Misma situación | Detectar en Preflight (Phase 1.6). Resolver manualmente |
| Cambios en SP_Permisos_Usuario_Efectivos | Si el nuevo SP retorna diferentes permisos, puede afectar autorización | Phase 4.4 debe detectar diferencias ANTES de cortar |

### 10.3 Puntos de restauración

| Punto | Fase | Estado |
|-------|------|--------|
| R0 | Antes de Phase 0 | Backup completo + tag git |
| R1 | Después de Phase 2 | Schema nuevo + columnas viejas aún existen |
| R2 | Después de Phase 3 | Datos migrados + columnas viejas aún existen |
| R3 | Después de Phase 5 | SPs nuevos + columnas viejas aún existen |
| R4 | Después de Phase 8 | Migración completa + backup post-cutover |

### 10.4 Scripts UP / DOWN

Cada fase debe tener:

- `FASE_N_UP.sql` — Migración hacia adelante
- `FASE_N_DOWN.sql` — Rollback de esa fase

Los scripts DOWN deben probarse antes de la migración.

### 10.5 Compatibility Matrix

La coexistencia de columnas legacy **no garantiza** compatibilidad automática entre versiones. El estado `⚠️` indica que la compatibilidad depende de condiciones que deben verificarse explícitamente.

**Estados del schema**:
- **OLD**: Schema original (columnas legacy son las únicas)
- **EXPANDED (+legacy)**: Schema con nuevas tablas/columnas + legacy KEEP. Las columnas legacy aún existen y son funcionales
- **MIGRATED (+legacy)**: Datos migrados a nuevas estructuras. Columnas legacy existen como compatibilidad, pero **el nuevo modelo es la fuente primaria**. WRITE en columnas legacy está **prohibido** después de MIGRATE
- **CONTRACTED (-legacy)**: Columnas legacy eliminadas. Schema final

| App | DB Schema | SPs | Compatibilidad | Condición |
|-----|-----------|-----|---------------|-----------|
| OLD | OLD | OLD | ✅ | Estado base |
| OLD | EXPANDED (+legacy) | OLD | ✅ | Schema expandido. SPs viejos solo ven legacy. Sin datos migrados aún |
| OLD | MIGRATED (+legacy) | OLD | ⚠️ | **Seguro solo antes de writes productivos de NEW app**. Si NEW app ha creado/modificado datos usando el nuevo modelo (p.ej., multi-tenant), el legacy puede no reflejar esos cambios. Rollback recomendado: restore completo |
| OLD | MIGRATED (+legacy) | NEW | ❌ | Contrato de SPs puede haber cambiado. No compatible |
| NEW | EXPANDED (+legacy) | NEW | ⚠️ | Válido solo para validación controlada (smoke tests). No liberar tráfico productivo sin migración de datos completa |
| NEW | MIGRATED (+legacy) | NEW | ✅ | **Estado operativo post-cutover** — NEW app + NEW SPs + datos migrados + legacy presente para contingencia |
| NEW | CONTRACTED (-legacy) | NEW | ✅ | **Estado final post-purge** — schema limpio |

**Reglas**:
1. **Pre-cutover** (antes de Phase 8.11 — liberar tráfico): rollback = restaurar OLD app + OLD SPs. No existen writes NEW, el legacy refleja el estado completo.
2. **Post-cutover** (después de liberar tráfico): rollback oficial = **full DB restore** + OLD SPs/triggers + OLD app. La presencia de columnas legacy **no constituye garantía de reversibilidad** porque NEW app puede haber escrito datos irrepresentables en el modelo legacy (multi-tenant, Platform Scope, etc.).
3. **Legacy columns**:
   - **Después de MIGRATE** (Phase 8.4-8.5): NEW application + NEW SPs/triggers tienen **WRITE PROHIBIDO** en columnas legacy. OLD application + OLD SPs/triggers *pueden* escribir legacy únicamente durante la ventana pre-cutover controlada (Phase 8.3-8.7, sin tráfico NEW productivo).
   - **Después de CUTOVER** (Phase 8.11 — tráfico NEW liberado): **ningún componente activo** debe escribir columnas legacy. Desde CUTOVER, legacy es **READ-ONLY** exclusivamente para compatibilidad/contingencia.
   - La infracción de esta regla (código nuevo escribiendo legacy) se considera un bug crítico de migración.

### 10.6 Post-Cutover Rollback Semantics

| Período | Rollback | Mecanismo | Garantía |
|---------|----------|-----------|----------|
| **Pre-cutover** (antes de liberar tráfico) | OLD app + OLD SPs | Restaurar app (git revert) + SPs/triggers (scripts DOWN) | ✅ Datos migrados preservados. Legacy refleja estado completo porque no hay writes NEW |
| **Post-cutover** (después de liberar tráfico) | **Full restore** | Restaurar backup DB completo + OLD SPs + OLD app | ✅ Pérdida de datos = último backup. No depende de consistencia legacy/NEW |
| **Contract** (después de Contract gate) | Solo restore completo | Backup pre-contract | ✅ Contract es irreversible sin restore |

**Regla**: PassPlat no implementa dual-write ni reverse migration automatizada. Desde el momento del CUTOVER (tráfico liberado), `OLD app + OLD SPs` deja de ser un rollback garantizado. El único mecanismo oficial post-cutover es **full database restore + OLD SPs + OLD application**.

**Definición de "writes NEW"**: Se considera NEW write cualquier operación realizada por la NEW application o por SPs migrados que genere estados no representables completamente mediante el modelo legacy (por ejemplo: múltiples UsuarioTenant para un mismo usuario, Platform Scope con IdUsuarioTenant=NULL, o futuras extensiones del modelo que no tengan correlato en columnas legacy).

**Precisión del backup de rollback**:
- El restore post-cutover utiliza **exclusivamente** el backup final pre-cutover (Phase 8.2), salvo que Disaster Recovery determine otro restore point.
- El rollback implica **pérdida de todas las transacciones posteriores** al backup restaurado. Dicha pérdida es aceptada como consecuencia del mecanismo oficial de rollback.
- Backup post-contract (Phase 8.20) debe preservarse como el nuevo baseline.

### 10.7 Criterios de abortar la migración

| Criterio | Cuándo se evalúa | Acción |
|----------|------------------|--------|
| Preflight detecta inconsistencias | Phase 1 | NO continuar. Revisar manualmente |
| SP_Permisos difiere entre versión actual y nueva | Phase 4 | NO continuar. Investigar |
| Login de administrador falla post-migración | Phase 8 | Rollback inmediato |
| Más de **5 errores críticos atribuibles a la migración** en monitoreo post-cutover | Phase 8 (30 min) | Rollback — evaluar si los errores son atribuibles a la migración, no a usuarios |
| Tiempo de migración excede ventana | Phase 8 | Si está en Phase 2-4, rollback. Si está en Phase 5+, evaluar caso por caso |

**Definición de error crítico atribuible a la migración**:
- Authentication failure (login que funcionaba pre-migración)
- Authorization regression (permiso que existía y dejó de existir)
- Data integrity violation (FK violation, NULL inesperado)
- SQL FK violation o constraint error
- Unhandled exception en flujos migrados

Los errores funcionales normales de usuarios (credenciales inválidas, formularios mal llenados, timeouts de red) **no activan rollback**.
