## 3. Acceptance Criteria — 11 Correcciones originales + 7 Hardening (CR-01..CR-07)

Cada corrección debe verificarse explícitamente antes de aprobar A0.4.

| # | Corrección | Sección A0.4 | Estado | Verificación |
|---|-----------|-------------|--------|-------------|
| 1 | **HTTP 428 no pertenece al SP**. El SP retorna códigos de negocio (`MULTIPLE_TENANTS`, `INVALID_CREDENTIALS`, etc.). La capa Application transforma a HTTP. | §6.1 flujo + §6.4 código C# | ✅ APLICADA | `SP_Auth_Login` nunca retorna HTTP. AuthService implementa `if (tenantsActivos.Count > 1) return 428` |
| 2 | **Endurecer migración UsuariosPermisos**. Validación pre-migración obligatoria: UP con `IdTenant ≠ Usuario.IdTenant` y UP con Usuario inexistente. Abortar si retorna filas. | §5.2 validaciones SQL | ✅ APLICADA | Dos queries de validación (`IdTenant ≠ Usuario.IdTenant`, LEFT JOIN Usuarios WHERE NULL). Abortar si hay filas |
| 3 | **UsuarioTenant.IdEstado = membership state**. IdEstado en UsuarioTenant es estado de la membresía, no estado global del usuario. Coexiste con Usuario.IdEstado (identidad global). | §4.2 tabla + §1.3 | ✅ APLICADA | Tabla documenta IdEstado como estado de membresía. Migración: copia directa de Usuario.IdEstado a UsuarioTenant.IdEstado |
| 4 | **EsTenantPrincipal exclusivo para background services**. No participa en login, autorización, resolución de tenant ni context-switch. | §4.3 + §7.2 | ✅ APLICADA | Solo UsuarioTenant principal para background services (PasswordExpiration). Login/context-switch usan `AuthenticationContext.IdTenant` o resolución explícita |
| 5 | **FK compuesta obligatoria**: `(Accesos.IdUsuarioTenant, Accesos.IdUsuario) → UsuarioTenant(Id, IdUsuario)`. Misma FK para UsuariosPermisos. Solo se evalúa cuando IdUsuarioTenant NOT NULL. | §8.1 + §1.4 | ✅ APLICADA | FK compuesta documentada en ambas tablas. Reemplaza triggers TR_Accesos_ValidarTenant y TR_UsuariosPermisos_ValidarTenant |
| 6 | **Validación ASIGNAR_PLATFORM_SCOPE**: `IdUsuarioTenant=NULL` requiere `Rol.IdTenant=NULL`. Implementar en `AccesoService.AsignarAccesoAsync`. | §8.6 código C# | ✅ APLICADA | Validación con código `PLATFORM_ROLE_MISMATCH`. Rol NULL requerido para Platform Scope |
| 7 | **SP_Permisos_Usuario_Efectivos**: Separar explícitamente Platform Scope (`Accesos.IdUsuarioTenant IS NULL AND Roles.IdTenant IS NULL`) de Tenant Scope (`IdUsuarioTenant IN UsuarioTenant activo`). | §6.2 SQL | ✅ APLICADA | WHERE con dos ramas: Platform OR Tenant. `WHERE a.IdUsuario = @IdUsuario` es invariante |
| 8 | **@IdTenant=NULL = Platform Context**. En SP_Permisos, NULL significa "solo permisos Platform". En login, NULL significa "resolver contexto". Nunca significa "desconocido". | §6.3 diagrama | ✅ APLICADA | AuthenticationContext.IdTenant NULL → SP_Permisos con NULL → solo Platform. AuthenticationContext.IdTenant=T → Platform + Tenant T |
| 9 | **Phase 6 antes de cutover (Phase 8)**: Código nuevo compilado + tests OK antes de Phase 8. Sin esto, BD nueva + app antigua es inválida. | §9 Phase 8 → §9 Phase 6 orden | ✅ APLICADA | Phase 6 (Application) completada y probada antes de Phase 8 (Cutover). Rollback de Phase 6 via git |
| 10 | **Rollback post-cutover requiere backup restore completo**: `git revert` solo es válido pre-cutover (mientras columnas legacy existen). Post-cutover, restaurar backup completo de BD + código. | §10 tabla (Phase 8) | ✅ APLICADA | Phase 8 rollback: restaurar backup completo. Pre-cutover: git revert suficiente porque columnas legacy existen |
| 11 | **Validación duplicados UsuarioTenant en Phase 1**: Detectar usuarios con mismo `(IdUsuario, IdTenant)` antes de migrar. | §4.5 + Phase 1 | ✅ APLICADA | Preflight (Phase 1) debe detectar duplicados potenciales antes de INSERT en UsuarioTenant |

| 12 | **CR-01 — Compatibility Matrix (Rollback)**. La coexistencia de columnas legacy no garantiza compatibilidad. `git revert` solo no constituye rollback completo. Agregar §10.5 con matriz App/DB/SP. | A0.4 §10.5 (nuevo) | ✅ APLICADA | Matriz 6x6 documentada. Rollback pre-cutover requiere restaurar código + SPs + triggers. git revert no es suficiente |
| 13 | **CR-02 — Preflight usuarios eliminados**. Phase 1 debe detectar Accesos/UsuariosPermisos con Usuario.Eliminado=1 y abortar si retorna filas. | A0.4 Phase 1.10 | ✅ APLICADA | Query de detección agregada. Criterio de abortar actualizado |
| 14 | **CR-03 — Unicidad UsuarioTenant(IdUsuario, IdTenant)**. Agregar UX_UsuarioTenant_Usuario_Tenant como capa DB que impide duplicados post-migración. | A0.4 §8.3 | ✅ APLICADA | UNIQUE(IdUsuario, IdTenant) agregado. Preflight y UNIQUE son capas complementarias |
| 15 | **CR-04 — Eliminar índice EXISTS imposible**. SQL Server no soporta subconsultas en filtros de índices. Validación solo en capa aplicación. | A0.4 §2.3 | ✅ APLICADA | Línea del índice opcional eliminada. `AccesoService.AsignarAccesoAsync` es el único enforcement |
| 16 | **CR-05 — Precisar Phase 8**. La aplicación NEW debe estar desplegada ANTES del schema/SP migration. La secuencia es: NEW app → backup → schema → data → SPs → smoke tests → auth validation → monitoring → release. | A0.4 Phase 8 | ✅ APLICADA → **REFINADA por CR-06** | Substituida por modelo Expand→Migrate→Deploy→Contract |
| 17 | **CR-06 — Expand→Migrate→Deploy→Contract**. Resolver contradicción entre CR-05 (NEW app antes de schema) y Compatibility Matrix (NEW app + OLD DB = ❌). Adoptar modelo donde EXPAND schema y MIGRATE SPs ocurren primero (con legacy KEEP), DEPLOY app después, y CONTRACT legacy es diferido. | A0.4 Phase 8 + §10.5 | ✅ APLICADA | Phase 8 reescrito con 4 etapas. Matriz actualizada con estados EXPANDED/MIGRATED/CONTRACTED. Phase 6 aclara desarrollo ≠ deploy |
| 18 | **CR-07 — Post-Cutover Rollback Semantics**. Legacy columns no garantizan rollback después de writes NEW. Distinguir pre-cutover (OLD app + OLD SPs válido) de post-cutover (solo full restore). Prohibir WRITE en legacy después de MIGRATE. Agregar Contract Approval Gate con 10+ condiciones y U01 como blocker potencial. | A0.4 §10.5, §10.6, Phase 8, §1.5 | ✅ APLICADA | Matriz: OLD\|MIGRATED\|OLD pasa de ✅ a ⚠️. Nueva §10.6 Post-Cutover Rollback Semantics. Phase 8: Contract Gate con condiciones. §1.5: legacy READ-ONLY |
| 19 | **CR-08 — Legacy READ-ONLY semantics: MIGRATE vs CUTOVER**. Distinguir: MIGRATE → NEW app/SPs no escriben legacy (OLD app/SPs pueden hacerlo en ventana controlada). CUTOVER → ningún componente activo escribe legacy. Legacy = READ-ONLY desde CUTOVER. | A0.4 §10.5 Regla 3 | ✅ APLICADA | Regla 3 reescrita con tres sub-reglas: post-MIGRATE (NEW no escribe, OLD puede en ventana), post-CUTOVER (legacy READ-ONLY), infracción = bug crítico |
| 20 | **CR-09 — Separar Phase 5 (desarrollo) de Phase 8.6 (promoción)**. Phase 5 = desarrollo/validación en QA. Phase 8.6 = PROMOTE a producción. Eliminar ambigüedad de "migrar SPs dos veces". | A0.4 Phase 5 + Phase 8.6 | ✅ APLICADA | Phase 5: nota "NO representa despliegue productivo". Phase 8.6: "PROMOTE: desplegar SPs/triggers nuevos (desarrollados en Phase 5)" |
| 21 | **CR-10 — Corregir encabezado A0.5**. Cambiar "5 Hardening (CR-01..CR-05)" por "7 Hardening (CR-01..CR-07)". Consistente con el resto del documento. | A0.5 §3 | ✅ APLICADA | Encabezado corregido |
| 22 | **CR-11 — Precisar backup para rollback post-cutover**. El backup utilizado debe ser el backup final pre-cutover (Phase 8.2), no "un backup cualquiera". El rollback implica pérdida de transacciones posteriores, aceptada como consecuencia del mecanismo oficial. | A0.4 §10.6 | ✅ APLICADA | §10.6 actualizado con precisión sobre backup y aceptación de pérdida de datos |

## 4. Key Decisions Summary

Todas las decisiones arquitectónicas tomadas durante A0:

| # | Decisión | ADR/Fuente | Efecto |

| D01 | Usuario = identidad global SIN IdTenant | ADR-001 | Eliminar columna. UsuarioTenant es la única fuente de membresía |

| D03 | Acceso Modelo A: IdUsuarioTenant? NULL = Platform Scope | ADR-003 | FK compuesta obligatoria. Platform Scope no crea membership |
| D04 | Platform Scope: IdUsuarioTenant=NULL + Rol.IdTenant=NULL | ADR-004 | JWT Platform ≠ Tenant permissions. Validación estricta en asignación |
| D05 | AuthenticationContext como Execution Context | ADR-005 | Reemplaza `idTenant ?? usuario.IdTenant`. Background usa EsTenantPrincipal |
| D06 | IdenExt.IdTenant = KEEP como INITIAL_CONTEXT | A0.2 | No es pertenencia. SP_ProvIden_BuscarUsuario no lo usa |
| D07 | MFA.IdTenant = KEEP como EXECUTION_CONTEXT | A0.2 | Revisar en A1 si debe migrar a UsuarioTenant |
| D08 | EsTenantPrincipal = solo background services | A0.4 §4.3 | Excluido de login, autorización, context-switch |
| D09 | HTTP 428 = responsabilidad de Application layer | A0.4 §6.1 | SP nunca decide HTTP. AuthService transforma códigos |
| D10 | 3 entidades/tablas migradas, 26 tablas KEEP, 1 tabla nueva (UsuarioTenant) | A0.2 | Usuario (-IdTenant), Acceso (+IdUsuarioTenant?), UsuarioPermiso (+IdUsuarioTenant?) |
| D11 | Triggers: 2 eliminar, 2 reescribir, 1 modificar | A0.4 §5 | FK compuesta reemplaza triggers de validación de tenant |
| D12 | SPs: 5 cambian directamente, 9 indirectamente | A0.4 §5 | Login, LoginExterno, UsuarioCrear, Dashboard, Permisos |
| D13 | 16 puntos de falla en servicios C# | A0.2 | 9 `idTenant ?? usuario.IdTenant`, 7 `usuario.IdTenant` directo |
| D14 | Preflight (Phase 1) = 10 queries read-only | A0.4 §9 Phase 1 | Aborta si detecta inconsistencias (1.2, 1.5, 1.6, 1.10). Nunca migrar datos corruptos |
| D15 | Rollback pre-cutover requiere restaurar código + SPs + triggers compatibles. Git revert solo no es suficiente. Post-cutover = backup restore completo. | A0.4 §10.5 | Compatibility Matrix con estados EXPANDED/MIGRATED/CONTRACTED (8 combinaciones). Mientras legacy existe, OLD app + OLD SPs es combinación válida de rollback |
| D16 | Cutover sigue modelo Expand→Migrate→Deploy→Contract. Schema EXPAND (con legacy KEEP) → MIGRATE SPs → DEPLOY app → CUTOVER tráfico → CONTRACT legacy (diferido). | A0.4 Phase 8 | Resuelve contradicción CR-05 vs matriz. Phase 6 (desarrollo) ≠ Phase 8.8 (deploy). Contract tiene Approval Gate |
| D17 | Rollback post-cutover = full restore. Legacy columns NO garantizan rollback después de writes NEW. Pre-cutover: OLD app + OLD SPs. Post-cutover: full DB restore + OLD SPs + OLD app. WRITE en legacy prohibido. | A0.4 §10.5 + §10.6 | Matriz marca OLD\|MIGRATED\|OLD como ⚠️. Contract Gate con 10+ condiciones. U01 es blocker potencial |
