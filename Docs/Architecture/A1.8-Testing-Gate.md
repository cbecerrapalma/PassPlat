## Scope

This gate validates behavioural correctness and tenant isolation of the multi‑tenant refactor. It is NOT a repeat of unit/regression tests — those are prerequisites. This is a functional certification gate.

### What is tested

| # | Phase | Test | Method | Expected |
|---|-------|------|--------|----------|
| 1 | A1.8.1 | Platform Login | `POST /api/auth/login/platform` | JWT with `TenantId=null`, `UsuarioTenantId=null`. Login succeeds. |
| 2 | A1.8.2 | Platform permissions | Call endpoint after Platform Login | Permissions are exclusively platform-scope (no tenant data). |
| 3 | A1.8.3 | Platform → Tenant | `POST /api/auth/switch-tenant/{validId}` | New JWT with `TenantId=X`, `UsuarioTenantId=Y`. Response is `AuthResponseDto`. |
| 4 | A1.8.3 | Switch‑tenant membership validation | SwitchTenant with valid + active `UsuarioTenant` | ✅ PASS — new JWT issued |
| 5 | A1.8.5 | Switch‑tenant no membership | SwitchTenant where user has no `UsuarioTenant` record | `403` or `401` with error code. Original JWT remains valid. |
| 6 | A1.8.4 | Tenant A → Tenant B | User with active memberships in both A and B | After switch: `TenantId` changes to B, `UsuarioTenantId` changes to B, permissions recalculated for B, A's data invisible. |
| 7 | A1.8.4 | Tenant B → Tenant A (round trip) | Switch back to A | Returns to A context with A's permissions. |
| 8 | A1.8.5 | Tenant → unauthorized Tenant | SwitchTenant where user has no active `UsuarioTenant` in target | `403 MEMBRESIA_INACTIVA`. Current JWT/context remains valid. |
| 9 | A1.8.6 | `GET /api/auth/mis-tenants` | Authenticated call | Returns ONLY tenants with `UsuarioTenant.Activo=true` AND `IdEstado=1 (Activo)`. Excludes inactive/deleted/inactive‑membership. |
| 10 | A1.8.6 | `GET /api/auth/mis-tenants` — no memberships | User with zero active UsuarioTenant | Returns empty array `[]`, not error. |
| 11 | A1.8.7 | Tenant data isolation — Dashboard | `GET /api/dashboard-enterprise/...` from tenant A vs B | A's data does NOT include B's records. B's data does NOT include A's. |
| 12 | A1.8.7 | Tenant data isolation — Usuarios | `GET /api/usuarios` from tenant A | Only users belonging to tenant A (via UsuarioTenant). |
| 13 | A1.8.8 | Platform aggregate visibility | `GET /api/dashboard-enterprise/...` from platform scope (`idTenant=null`) | Aggregate across all accessible tenants. |
| 14 | A1.8.5 | Inactive UsuarioTenant excluded | User with `UsuarioTenant.Activo=false` tries to switch | `403 MEMBRESIA_INACTIVA`. |
| 15 | A1.8.5 | Deleted user excluded | `Usuario.Eliminado=true` user | Login fails (`USER_NOT_FOUND`/`USER_INACTIVE`). `mis-tenants` excludes their memberships. |
| 16 | A1.8.9 | `JWT TenantId` consistency — Platform | Platform‑scope JWT | `TenantId` does NOT represent any tenant (claim absent OR semantically null). |
| 17 | A1.8.9 | `JWT UsuarioTenantId` consistency — Platform | Platform‑scope JWT | `UsuarioTenantId` does NOT represent any membership (claim absent OR semantically null). |
| 18 | A1.8.9 | `JWT TenantId` consistency — Tenant | Tenant‑scope JWT (after switch) | `TenantId` claim value == expected tenant Id. |
| 19 | A1.8.9 | `JWT UsuarioTenantId` consistency — Tenant | Tenant‑scope JWT (after switch) | `UsuarioTenantId` claim value == expected UsuarioTenant.Id. |
| 20 | A1.8.9 | Permission recalculation | Compare permission set before/after switch | Permissions change to reflect target tenant's roles. |

## Execution Sequence

Tests must run in this order to avoid cascading failures:

```
A1.8.0  Test data / fixtures setup
   ↓
A1.8.1  Platform authentication
         Test #1
   ↓
A1.8.2  Platform permissions
         Test #2
   ↓
A1.8.3  Platform → Tenant (tests 3–4)
   ↓
A1.8.4  Tenant → Tenant (tests 6–7)
   ↓
A1.8.5  Membership rejection (tests 5, 8, 14, 15)
   ↓
A1.8.6  mis-tenants (tests 9–10)
   ↓
A1.8.7  Tenant isolation (tests 11–12)
   ↓
A1.8.8  Platform aggregate visibility (test 13)
   ↓
A1.8.9  JWT integrity & context consistency (tests 16–19, 21–22)
   ↓
A1.8.10 Usuario.IdTenant audit (test 23)
   ↓
A1.8.11 Cross-tenant leakage (test 24)
   ↓
A1.8 FINAL GATE
```

### Failure classification

If a test FAILs, classify before touching production code:

- **TEST / FIXTURE**: Test logic, assertions, or test data setup is wrong.
- **CONTRATO**: The API contract (request/response shape, status codes) is incorrect or undocumented.
- **IMPLEMENTACIÓN**: The code behaviour does not match the agreed contract.
- **SECURITY**: Authentication or authorization bypass detected.
- **DATA ISOLATION**: Cross-tenant data leak detected.
- **REGRESSION**: A previously passing unit/E2E test now fails.

> **Hard rule for A1.8**: A single cross-tenant data isolation failure (DATA ISOLATION) blocks gate closure regardless of the other 23 tests.
>
> **403 verification note**: An unexpected `403` response is NOT automatically a security PASS. Before classifying as PASS, verify:
> - the user genuinely lacks the required membership;
> - the error code matches the contract (e.g. `MEMBRESIA_INACTIVA`);
> - the original JWT remains valid when the response is `401`;
> - no information about the target tenant was leaked in the response body.

## Documented GAP: Tenant→Platform Switch

**A1.9 — Switch‑to‑Platform**

### Current state
There is no endpoint `POST /api/auth/switch-to-platform` or equivalent. A user authenticated at tenant scope (`TenantId=X`, `UsuarioTenantId=Y`) cannot return to platform scope without re‑logging in via `POST /api/auth/login/platform`.

### Constraint
No workaround may use `Usuario.IdTenant` as execution context. The absence of a switch‑to‑platform endpoint is intentional: the current model requires an explicit authentication event (login) to establish platform scope. This prevents privilege escalation from a compromised tenant JWT.

### When to implement
- A1.9, after A1.8 gate is signed.
- Must include: new endpoint, JWT re‑issuance with `TenantId=null`/`UsuarioTenantId=null`, permission recalculation for platform scope, session invalidation for old tenant JWT.
- Must NOT introduce `Usuario.IdTenant` as execution context.
