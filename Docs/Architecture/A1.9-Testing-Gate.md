## 1. Objetivo

Implementar `POST /api/auth/switch-to-platform` que permita a un usuario con JWT tenant-scoped obtener un JWT platform-scoped, **sin** que esto constituya una elevación de privilegios.

### Flujo requerido

```
Tenant JWT
   ↓
Autenticación válida
   ↓
Autorización PLATFORM
   ↓
Nuevo AuthenticationContext (IdTenant=null, IdUsuarioTenant=null)
   ↓
PermissionClaimBuilder (Platform scope)
   ↓
Nuevo JWT Platform
```

### Flujo prohibido (privilege escalation)

```
Tenant JWT
   ↓
"quitar TenantId"
   ↓
PLATFORM  ← NO VÁLIDO
```

---

## 2. Autorización PLATFORM

### Condición de autorización

Un usuario puede pasar a Platform Scope si y solo si:

1. El JWT de entrada es válido (firma verificada, no expirado).
2. El usuario identificado por el JWT existe y está activo (`IdEstado = 1`, `Eliminado = 0`).
3. El usuario tiene **al menos una membresía UsuarioTenant activa** (`Activo = 1`) en **cualquier tenant**.
4. El usuario tiene **rol PLATFORM_** (`IdRol IN (1, 2, 3, 4)` — los roles PLATFORM_* definidos en A1.3) en **cualquier UsuarioTenant activa**.

### Regla de seguridad

- **No** se asume que "todo usuario con JWT tenant puede hacerlo".
- **No** se asume que "todo usuario activo puede hacerlo".
- La autorización PLATFORM requiere **rol explícito PLATFORM_** asociado a una membresía activa.

---

## 3. Claims del JWT Platform

| Claim | Valor |
|-------|-------|
| `TenantId` | `null` / ausente |
| `UsuarioTenantId` | `null` / ausente |
| `IdUsuario` | ID del usuario (preservado) |
| `IdApp` | Preservado |
| `permiso` | Permisos PLATFORM_* exclusivamente |

### Permisos

- Los permisos del tenant anterior **deben desaparecer completamente**.
- El nuevo contexto contiene **únicamente** permisos PLATFORM_*.
- **No** se permite unión: `Tenant permissions + Platform permissions`.

---

## 4. Invalidación del JWT anterior

### Mecanismo

- **Invalidación inmediata** mediante revocación de la sesión asociada al JWT de entrada.
- El endpoint debe invalidar el `refreshToken` y la sesión activa del usuario en el tenant de origen.
- El JWT de acceso anterior **no debe ser reutilizable** después del switch.

### Justificación

- "Emitir un JWT nuevo" no invalida automáticamente el anterior.
- Un JWT anterior reutilizable después del switch constituye un fallo de seguridad (session fixation / stale context).

## 11. Hallazgos arquitectónicos (revisión de código)

### 11.1 PermissionClaimBuilder — Platform vs Tenant distinction

**Archivo**: `PassPlat.Aplicacion/Services/Authentication/Claims/PermissionClaimBuilder.cs:26-37`

El `PermissionClaimBuilder` ya distingue tres contextos:

```csharp
if (context.IdTenant == null)
{
    // PLATFORM scope
    result = await _authRepo.ObtenerCodigosPermisosPlatformAsync(context.IdUsuario, context.IdApp, ct);
}
else if (context.IdUsuarioTenant.HasValue)
{
    // Tenant scope (UsuarioTenant)
    result = await _authRepo.ObtenerCodigosPermisosPorUsuarioTenantAsync(context.IdUsuarioTenant.Value, context.IdApp, ct);
}
else
{
    // Tenant scope (legacy)
    result = await _authRepo.ObtenerCodigosPermisosPorUsuarioAsync(context.IdUsuario, context.IdTenant.Value, context.IdApp, ct);
}
```

**Hallazgo**: La distinción platform/tenant ya está implementada. Un `AuthenticationContext` con `IdTenant=null` y `IdUsuarioTenant=null` produce permisos PLATFORM_* exclusivamente.

### 11.2 AuthenticationTokenIssuer — JWT Platform generation

**Archivo**: `PassPlat.Aplicacion/Services/Authentication/AuthenticationTokenIssuer.cs:43-62`

```csharp
private static List<Claim> BuildIdentityClaims(AuthenticationContext context, string jti)
{
    var claims = new List<Claim>
    {
        new(ClaimTypes.NameIdentifier, context.IdUsuario.ToString()),
        new("IdApp", context.IdApp.ToString()),
        new(JwtRegisteredClaimNames.Jti, jti)
    };

    if (context.IdTenant.HasValue)
        claims.Add(new Claim("TenantId", context.IdTenant.Value.ToString()));

    if (context.IdUsuarioTenant.HasValue)
        claims.Add(new Claim("UsuarioTenantId", context.IdUsuarioTenant.Value.ToString()));

    if (context.EsSistema)
        claims.Add(new Claim("is_system", "true"));

    return claims;
}
```

**Hallazgo**: Cuando `IdTenant=null` y `IdUsuarioTenant=null`, los claims `TenantId` y `UsuarioTenantId` **no se agregan** al JWT. Esto cumple el contrato de A1.9 sin código adicional.

### 11.3 AuthenticationTokenService — Token emission pipeline

**Archivo**: `PassPlat.Aplicacion/Services/Authentication/AuthenticationTokenService.cs:27-101`

El pipeline `EmitirTokensYCrearSesionAsync`:
1. `PermissionClaimBuilder.BuildPermissionClaimsAsync(context, ct)` — obtiene permisos
2. `AuthenticationTokenIssuer.Generate(context, permisoClaims)` — genera JWT
3. `SessionManager.CreateSessionAsync(...)` — crea sesión en BD

**Hallazgo**: El pipeline ya acepta un `AuthenticationContext` con `IdTenant=null`. El `SwitchToPlatformAsync` puede reutilizar este pipeline directamente.

### 11.4 Authorization PLATFORM — Rol PLATFORM_*

**Archivo**: `PassPlat.Datos/Repositories/AuthRepository.cs:142-160`

```csharp
public async Task<Result<IReadOnlyList<string>>> ObtenerCodigosPermisosPlatformAsync(int idUsuario, int idApp, CancellationToken ct)
{
    var codigos = await Context.Set<Acceso>()
        .Where(a => a.IdUsuario == idUsuario && a.IdApp == idApp && a.Activo && a.IdUsuarioTenant == null)
        .SelectMany(a => a.Rol!.RolesPermisos)
        .Where(rp => rp.Activo)
        .Select(rp => rp.Permiso!.Codigo)
        .Distinct()
        .ToListAsync(ct);
    return Result<IReadOnlyList<string>>.Success(codigos);
}
```

**Hallazgo CRÍTICO**: La autorización PLATFORM se basa en `Acceso` con `IdUsuarioTenant == null`. Si un usuario no tiene `Acceso` con `IdUsuarioTenant == null`, obtendrá **cero permisos PLATFORM_*. Esto es correcto** — no se requiere un rol explícito PLATFORM_* como condición previa; el acceso a permisos platform se resuelve naturalmente desde la tabla `Acceso`.

**Sin embargo**: Para evitar privilege escalation, el endpoint `SwitchToPlatform` debe **verificar explícitamente** que el usuario tenga al menos un `Acceso` con `IdUsuarioTenant == null` y `Activo == true` antes de emitir el JWT platform. Si no lo tiene, debe retornar 403.

### 11.5 Invalidación del JWT anterior — SessionManager

**Archivo**: `PassPlat.Aplicacion/Services/Authentication/SessionManager.cs:58-68`

```csharp
public async Task<Result> RevokeSessionAsync(Guid sessionId, CancellationToken ct)
{
    var result = await _sesionRepo.RevocarSesionAsync(sessionId, ct);
    ...
}
```

**Hallazgo**: Existe `SessionManager.RevokeSessionAsync` que revoca una sesión por ID. Para invalidar el JWT anterior:

1. Extraer `jti` del JWT de entrada (claim `Jti`).
2. Buscar la sesión activa del usuario con ese `jti`.
3. Llamar a `RevokeSessionAsync(sessionId)`.

**Gap**: No existe un método para buscar sesión por `jti`. Se requiere un método adicional en `SesionRepository` o `SessionManager`.

### 11.6 SwitchTenant existente — Patrón a seguir

**Archivo**: `PassPlat.Aplicacion/Services/SPro/AuthService.cs:551-596`

El `SwitchTenantAsync` ya implementa el patrón correcto:
1. Valida membresía activa (`ObtenerActivoPorTenantAsync`)
2. Crea `AuthenticationContext` con `IdUsuarioTenant`
3. Llama a `_tokenService.LoginAsync(authContext, ct)`
4. Retorna `AuthResponseDto`

**Patrón para `SwitchToPlatformAsync`**:
1. Validar que el JWT de entrada es válido (ya hecho por el middleware)
2. Extraer `IdUsuario` del JWT
3. Verificar que el usuario tiene `Acceso` platform activo (`IdUsuarioTenant == null`)
4. **Invalidar** la sesión del JWT de entrada (revocar sesión anterior)
5. Crear `AuthenticationContext` con `IdTenant=null, IdUsuarioTenant=null`
6. Llamar a `_tokenService.LoginAsync(authContext, ct)` — esto crea una nueva sesión
7. Retornar `AuthResponseDto` con `IdTenant=0`
