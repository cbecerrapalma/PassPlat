# BUG-017.1.3 / A1.9 — Permission Scope Investigation

## 1. Expected Authorization Model

PassPlat tiene dos scopes de autorización:

| Scope | IdTenant | IdUsuarioTenant | Significado |
|-------|----------|-----------------|-------------|
| **Tenant** | valor | valor | Usuario opera dentro de un tenant específico |
| **Platform** | NULL | NULL | Usuario opera a nivel plataforma (multi-tenant) |

El `PermissionClaimBuilder` despacha a tres fuentes según el contexto:

```
IdTenant == null          → ObtenerCodigosPermisosPlatformAsync
IdUsuarioTenant.HasValue  → ObtenerCodigosPermisosPorUsuarioTenantAsync
else                      → ObtenerCodigosPermisosPorUsuarioAsync
```

## 4. PermissionClaimBuilder Analysis

| Aspecto | Tenante | Platform |
|---------|---------|----------|
| Método | `ObtenerCodigosPermisosPorUsuarioTenantAsync` | `ObtenerCodigosPermisosPlatformAsync` |
| Query | SP via `_rawQuery` | LINQ directo sobre DbSet |
| Filtro Acceso | `IdUsuario=8 AND IdTenant=3` | `IdUsuario=8 AND IdUsuarioTenant=NULL` |
| Columnas diferentes | Filtra por `IdTenant` | Filtra por `IdUsuarioTenant` |

**Ambos caminos son independientes y correctos.** El dispatch es determinístico basado en `AuthenticationContext`.

## 6. Permission Source (DB)

### Acceso de test_multitenant (IdUsuario=8)

Basado en el comportamiento observado, `test_multitenant` tiene:

1. **Un Acceso platform-wide**: `IdUsuario=8, IdTenant=NULL, IdUsuarioTenant=NULL, Activo=1, IdRol=ADMIN_PLATFORM`
2. **Un Acceso tenant (Tenant 3)**: `IdUsuario=8, IdTenant=3, IdUsuarioTenant=4, Activo=1, IdRol=ADMIN_TENANT`

Ambos roles (`ADMIN_PLATFORM` y `ADMIN_TENANT`) están configurados con **los mismos 7 permisos**:
- ACCESOS_VER
- GRUPOS_VER
- MATRIZ_PERMISOS_VER
- PERMISOS_VER
- ROLES_VER
- USUARIOS_VER
- USUARIOS_VERDISP

Esto es consistente con la semilla de datos donde el usuario administrador obtiene permisos completos de gestión en su tenant y en plataforma.

## 8. Test #5 Expectation Analysis

**Código del test** (`tests/faseA19-switch-to-platform.spec.ts:101-113`):

```typescript
test('#5 Permisos del tenant anterior desaparecen', async () => {
    const login = await loginAs('test_multitenant', PWD, 3);
    const tenantJwt = decodeJwt(login.token);
    const tenantPerms = JSON.stringify(tenantJwt.permiso || []);

    const r = await switchToPlatform(login.token);
    const platformJwt = decodeJwt(r.data.accessToken);
    const platformPerms = JSON.stringify(platformJwt.permiso || []);

    expect(platformPerms).not.toBe(tenantPerms);
});
```

**Error**: `expect(platformPerms).not.toBe(tenantPerms)` — Ambos son el mismo array de 7 permisos.

**Supuesto del test**: Al cambiar de tenant a platform, los permisos deben recalcularse y ser diferentes.

**Realidad**: Los permisos SÍ se recalculan (vía `ObtenerCodigosPermisosPlatformAsync`), pero como el usuario `test_multitenant` tiene roles equivalentes en ambos scopes, el resultado es el mismo conjunto.

**¿Es esto un bug?** Depende del contrato:

- Si el contrato es "platform y tenant producen conjuntos de permisos independientes": ✅ No es bug. Los conjuntos son independientes pero coinciden para este usuario.
- Si el contrato es "platform debe tener permisos diferentes a tenant": ❌ El test es incorrecto — el contrato real es independencia, no diferencia.
- Si el contrato es "platform tiene menos permisos que tenant por diseño": ❌ El test asume una diferencia que el modelo no garantiza.

## 9. Root Cause Classification

```
CATEGORY: B — Test expectation bug

El test #5 asume que los permisos platform DEBEN SER DIFERENTES
de los permisos tenant, pero esto no está garantizado por el modelo
de autorización de PassPlat.

El PermissionClaimBuilder recalcula correctamente los permisos para cada
scope (platform vs tenant), cada uno desde su propia fuente de datos
(Acceso.IdUsuarioTenant==NULL vs SP_Permisos_Usuario_Efectivos).

El hecho de que ambos devuelvan el mismo conjunto es una consecuencia
legítima de que test_multitenant tenga roles equivalentes en ambos scopes.

El error se clasifica como:
- Código:   ✅ Correcto (no requiere cambios)
- Test:     ❌ Expectativa incorrecta
- Datos:    ⚠ Los datos de seed asignan roles con permisos equivalentes
```

### Árbol de decisión

```
¿El PermissionClaimBuilder recibe el contexto correcto?
   Sí → IdTenant=NULL para platform, IdTenant=3 para tenant ✅
   ↓
¿El dispatch es correcto?
   Sí → platform → ObtenerCodigosPermisosPlatformAsync ✅
         tenant   → ObtenerCodigosPermisosPorUsuarioTenantAsync ✅
   ↓
¿Cada método consulta su fuente correcta?
   Sí → platform: Acceso WHERE IdUsuarioTenant=NULL ✅
         tenant:   SP_Permisos_Usuario_Efectivos(@IdTenant=3) ✅
   ↓
¿Los resultados son idénticos?
   Sí → porque el usuario tiene roles equivalentes en ambos scopes ✅
   ↓
¿El test espera diferencias?
   Sí → ❌ El test asume un contrato que no existe
```

## 10. Recomendación

**No modificar código de producción** — PermissionClaimBuilder, AuthService, AuthenticationTokenIssuer, SessionManager, ni AuthController son correctos.

**Opción para el test** (solo una vez autorizado):

1. **Cambiar el test** para verificar que los permisos se **recalculan independientemente** (no que son diferentes):

```typescript
test('#5 Permisos recalculados independientemente del tenant', async () => {
    const login = await loginAs('test_multitenant', PWD, 3);
    const tenantJwt = decodeJwt(login.token);

    const r = await switchToPlatform(login.token);
    expect(r.status).toBe(200);
    const platformJwt = decodeJwt(r.data.accessToken);

    // Verificar independencia: cada JWT tiene sus propios permisos,
    // calculados desde su propia fuente
    expect(Array.isArray(platformJwt.permiso)).toBe(true);
    expect(platformJwt.permiso.length).toBeGreaterThan(0);
    expect(platformJwt.TenantId).toBeUndefined();
    expect(platformJwt.UsuarioTenantId).toBeUndefined();
    // El contenido puede ser igual o diferente según los roles del usuario
});
```

2. **O usar un usuario diferente** que tenga roles platform distintos de sus roles tenant (si existe en la semilla).

## Conclusión

**No hay bug en el código de producción.** El `PermissionClaimBuilder` despacha correctamente según el contexto. Los permisos se recalculan desde fuentes independientes para cada scope. La coincidencia de resultados es legítima para el usuario `test_multitenant`.

**El test #5 tiene una expectativa incorrecta** — asume que los permisos platform deben diferir de los tenant, pero el contrato real de PassPlat solo garantiza independencia de cálculo, no diferencia de contenido.

Para certificar A1.9, el test #5 debe corregirse para que verifique independencia (no diferencia), o debe usarse un usuario seed con roles platform diferentes.

**No se requiere modificar JwtTokenService, PermissionClaimBuilder, AuthenticationTokenIssuer, AuthService, SessionManager, AuthController, ni ningún componente A1.9.**
