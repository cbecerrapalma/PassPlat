## 1. Objetivo

Clasificar los candidatos de caché por **evidencia de ROI** (frecuencia lectura/escritura, tamaño, prioridad) ANTES de escribir código, usando el canal ya establecido `ICacheService` de CBP.Caching. Priorizar por impacto real sobre el hot path y consistencia de datos.

## 3. Orden incremental (respaldado por ROI)

| Orden | Dato | Código | Por qué primero |
|---|---|---|---|
| **1** | PolíticaPwd (CAD-001) | `PoliticaPwdRepository` → `ICacheService` | Hot-para de autenticación; 6-8 queries/login → máximo beneficio query/s |
| **2** | ConfigTenant (CAD-002) | `ConfigTenantRepository` → `ICacheService` | Cada request tenant; valido y barato |
| **3** | Apps catálogo (CAD-005) | `AppRepository` → `ICacheService` | Catálogo pequeño; low effort |

Roles/Permisos y Menús quedan **fuera** (claims JWT ya cubren permisos; menús de frecuencia baja).

## 4. Patrón de implementación (siguiente `ConfigAppRepository` CAN-004)

```
key builder → GetAsync<T> (hit) → si miss: Query BD root → SetAsync(key, data, TTL) → Return
Escritura (Create/Update/Deactivate/Change) → RemoveAsync(keys afectados) → no datos obsoletos
```

- **Claves normalizadas**: `politicapwd:applicable:{idTenant}:{idApp}`, `politicapwd:global`, `configtenant:tenant:{idTenant}`, `app:catalog`.
- **TTL configurable**: `AbsoluteExpiration`/`SlidingExpiration` corto (30-60s) para hot-path; aislado.
- **Invalidación automática en escritura** (Create/Update/Deactivate/SP_Pwd_Cambiar).
- **Hit-ratio medible**: logging estructurado en los métodos de repositorio marcando cache-hit/miss.
- **CBP.Caching**: solo a través de `ICacheService` (regla 18 AGENTS). No novoh `IMemoryCache`.
