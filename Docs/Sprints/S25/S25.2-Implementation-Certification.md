## Objetivo

Eliminar la fuga de EF Core del contrato de Unidad de Trabajo: `IUnitOfWorkAsync`/`IUnitOfWorkSync`
pasan a ser interfaces **no genéricas y sin EF**, mientras la constraint `where TDbContext : DbContext`
y el acceso a `DbContext` permanecen **exclusivamente en las implementaciones**
`UnitOfWorkAsync<TDbContext>` / `UnitOfWorkSync<TDbContext>`.

```
Antes (S24):  IUnitOfWorkAsync<TDbContext> + using EF + DbContext/DbSet en el contrato
Después (S25.2): IUnitOfWorkAsync  (agnóstico) + EF SOLO en UnitOfWorkAsync<TDbContext>
```

| Paso | Resultado |

## Hallazgos

1. **`CbpCatalog.cs` (categoría DATA) no prohíbe EF** → los tests S24 existentes no detectaban
   la fuga EF de Data.Abstractions; el gate CONTRACT PURITY es un test nuevo, no una modificación S24.
2. **`SaveEntitiesAsync`: 0 consumidores externos** → conservado en contrato por decisión
   (familia SaveChanges).
3. **`HasActiveTransaction`: 0 externos pero usado internamente** por `ExecuteInTransaction*`
   → fuera de contrato, conservado en impl.
4. **Discrepancia de versiones EF** (`Asynchronous` 10.0.11 vs `Synchronous` EF.Relational 10.0.9)
   = **fuera de S25.2** (deuda F3/S27).
5. **`UnitOfWorkServiceExtensions.cs`** (CBP.Services.Async/Sync): usan `GetCustomService` de DI,
   sin el tipo genérico — seguros, no tocados.
