# S29.0 — F3 EF Version Skew Discovery (READ-ONLY)

> **Sprint**: S29 · **Fase**: S29.0 (Discovery) · **Modo**: READ-ONLY — sin modificar CBP, sin actualizar paquetes, sin tocar .csproj, sin implementar A/B/C.
> **Objetivo**: Documentar con evidencia el estado real del skew de versiones EF Core (Microsoft.EntityFrameworkCore / .Relational) entre el stack **Sync** (`CBP.Data.Synchronous`, `CBP.Services.Sync`) y el stack **Async** (`CBP.Data.Asynchronous`, `CBP.Data.Utilities`, `CBP.Data.Specifications`, `CBP.Services.Async`), y su impacto real en consumidores (CBP hosts, PassPlat, InventaNet).
> **Fecha de ejecución**: 2026-08-14 · **Sesión**: S29 Discovery (continuación de S28).

---

## 1. Resumen ejecutivo

- El skew existe **únicamente en 2 proyectos productores** (10.0.9): `CBP.Data.Synchronous` y `CBP.Services.Sync`. Los **8 proyectos** en vía 10.0.11 resuelven correctamente el ultimo patch.
- **PasPlat runtime = unificado 10.0.11** (ningún proyecto PassPlat resuelve/copia 10.0.9 en assets). El stack sync solo llega a PassPlat vía `PassPlat.CBP.Architecture.Test` (único proyecto PassPlat que lo referencia) y aun allí `project.assets.json` resuelve **10.0.11** (highest-wins).
- **Hallazgo nuevo**: existe un segundo consumidor del stack sync fuera de CBP y PassPlat: **`D:\CODIGOS\InventaNet`** (aplicación WinForms `net10.0-windows`). `Inventa.Data` → `CBP.Data.Synchronous`; `Inventa.Application` → `CBP.Services.Sync`. Sus assets resuelven EF **10.0.7/10.0.8** (de sus propias referencias directas), no 10.0.9 ni 10.0.11.
- El delta 10.0.9 → 10.0.10 → 10.0.11 es **bugfix/security lane** (patches mensuales de .NET 10 LTS); sin breaking changes documentados a nivel API en las tres patch releases. Assembly version se incrementa por patch (10.0.9.0 → 10.0.10.0 → 10.0.11.0), lo que **no es un breaking change de API** pero sí cambia la versión fuerte del ensamblado.
- **Parity Async↔Sync verificada a nivel API** (Roslyn/Sharplens): 8/8 read methods, 7/7 raw-query, 5/5 UoW. Ambas vías exponen exactamente el mismo contrato; la diferencia es solo de asincronía y de versión EF compilada.
- **DEUDA-005/006/007/F8**: 005 y 007 son **independientes de F3** (placeholders de UoW y Detach sin consumidores de producción). 006 (`Query()/IQueryable`) tiene 1 consumidor real (`CachingRepositoryDecorator.cs:45`) y es **RETAIN** — su resolución de tipo `IQueryable` con EF no cambia por el bump de patch. F8 (FrameworkReference ASP.NET) ya tiene decisión RETAIN de S25, ajena a F3.

## 4. Evidencia 2 — Delta 10.0.9 → 10.0.10 → 10.0.11

### 4.1 Fechas oficiales (.NET 10 LTS)

| Versión | Fecha release | Canal |
|---|---|---|
| 10.0.9 | 2026-06-09 | Patch monthly |
| 10.0.10 | 2026-07-14 | Patch monthly |
| 10.0.11 | 2026-08-11 | Patch monthly |

- .NET 10 es LTS hasta 2028-11-14. Política oficial de EF: *"Supported releases are patched for security and other critical bugs. Always use the latest patch of a given release."*
- Las patch releases no introducen breaking changes documentados (los breaking changes de EF Core se documentan por major/minor). No hay breaking changes anunciados para 10.0.10/10.0.11.

### 4.2 Evidencia local de ensamblados (caché NuGet ~\.nuget\packages)

| Versión | FileVersion | AssemblyVersion |
|---|---|---|
| 10.0.9 | 10.0.926.27113 | 10.0.9.0 |
| 10.0.10 | 10.0.1026.x | 10.0.10.0 |
| 10.0.11 | 10.0.1126.x | 10.0.11.0 |

**Hallazgo técnico**: EF Core usa **assembly version por patch** (no "10.0.0.0" estable). Esto significa que los ensamblados de 10.0.9, 10.0.10 y 10.0.11 tienen **versión fuerte distinta**. En carga con .NET app-local (deps.json) la versión resuelta gana por highest-wins y no hay collision-loader, pero en escenarios de *shadow-copy / provider loading* la mezcla de vías Sync (10.0.9) y Async (10.0.11) en un mismo proceso expone dos ensamblados con el mismo simple name y distinta AssemblyVer → riesgo de `FileLoadException`/`MissingMethodException` si ambos se cargan a la vez por rutas distintas.

### 4.3 Clasificación

| Transición | Tipo | Riesgo API |
|---|---|---|
| 10.0.9 → 10.0.10 | Bugfix/security | Ninguno |
| 10.0.10 → 10.0.11 | Bugfix/security | Ninguno |

**Conclusión**: no existe razón funcional para retener 10.0.9 en los productores Sync salvo conservación de estado; el bump a 10.0.11 alinea la vía Sync con la vía Async y con el runtime real de PassPlat.

## 5. Evidencia 3 — Parity Async ↔ Sync (Roslyn/Sharplens)

### 5.1 IReadRepositoryAsync vs IReadRepositorySync (8/8)

| Async | Sync |
|---|---|
| `Query()` | `Query()` |
| `GetByIdAsync<TId>` | `GetById<TId>` |
| `GetAllAsync` | `GetAll` |
| `ExistsAsync<TId>` | `Exists<TId>` |
| `FirstOrDefaultAsync` | `FirstOrDefault` |
| `WhereAsync` | `Where` |
| `AnyAsync` | `Any` |
| `CountAsync` | `Count` |

### 5.2 IRawQueryRepositoryAsync vs IRawQueryRepositorySync (7/7)

QuerySP* / QuerySPWithOutput* / ExecuteSP* / ScalarSP* / QuerySPMultiple* / QuerySql* / ExecuteSql* — idénticos salvo sufijo `Async`.

### 5.3 IUnitOfWorkAsync vs IUnitOfWorkSync (5/5)

`RawQuery` property, `SaveChanges*`, `SaveEntities*`, `ExecuteInTransaction*` (+ getter implícito). `IUnitOfWorkAsync : IDisposable, IAsyncDisposable`; `IUnitOfWorkSync : IDisposable`.

### 5.4 Estructura de implementación (parity de archivos)

- `RepositoryAsync<T>`: partials `Read.cs`, `Write.cs`, `Pagination.cs`, `Batch.cs`.
- `RepositorySync<T>`: partials `Read.cs`, `Write.cs`, `Pagination.cs` (sin Batch — diferencia conocida).
- `RawQueryRepositoryAsync`/`Sync`: classes internal sealed; interface `IRawQueryRepositoryAsyncSqlServer`/`SyncSqlServer` en cada proyecto (no en Abstractions).
- `RepositoryFactoryAsync`/`Sync`: internal; `IUnitOfWorkAsync`/`IUnitOfWorkSync` en Abstractions sin EF.

**Conclusión parity**: ambas vías son la *misma superficie de contrato*; la única diferencia de versión EF es de compilación (Strong AssemblyVer), no de API consumida.

## 6. Evidencia 4 — Realineación DEUDA-005/006/007/F8 respecto a F3

| Deuda | ¿Depende de F3? | Evidencia |
|---|---|---|
| **DEUDA-005** (`GetRepository`/`GetCustomRepository` placeholders en UoW) | **No funcionalmente** | Implementaciones en `UnitOfWorkAsync.cs:57/67` y `UnitOfWorkSync.cs:59/69` retornan vía `_factory.CreateRepository`/`CreateCustomRepository` (factories internas propias, sin `IRepositoryAsync<TEntity>` genérico que dependa del tipo EF). 0 consumidores en PassPlat (grep S27). Independiente de la versión de EF. |
| **DEUDA-006** (`Query()/IQueryable` RETAIN provisional) | **Parcial (RETAIN)** | `IQueryable<T>` es tipo EF; pero con 1 solo consumidor (`CachingRepositoryDecorator.cs:45`) y la resolución de `IQueryable` no cambia entre 10.0.9 y 10.0.11. RETAIN justificado (decisión S25.1 §10). |
| **DEUDA-007** (`Detach`/`DetachAsync` sin uso prod) | **No** | Existe en Sync (`Detach`), ausente en Async; parity a decidir (S25.1 §4). No es función de la versión de EF. |
| **F8** (FrameworkReference ASP.NET en `CBP.Authentication.Abstractions`) | **No** | Decisión RETAIN ya formalizada en S25; ámbitos de infraestructura (log/JWT/WebApi) sin relación con EF. |

**Conclusión realineación**: El registro S27 marcó estas deudas con "dependencia F3" por **agrupación histórica** (todas "requieren tocar CBP"), no por causalidad de versión de paquete. El bump de EF es **ortogonal** a los placeholders de UoW y a Detach. Solo DEUDA-006 tiene un vínculo real (tipo `IQueryable`), pero con RETAIN ya decidido y sin cambio de superficie en el patch lane.

## 7. Impacto PassPlat

- **Build actual**: PassPlat compila contra la vía Async 10.0.11; el único proyecto que referencia el stack sync (`PassPlat.CBP.Architecture.Test`) **resuelve 10.0.11** en su `project.assets.json` → el runtime de PassPlat ya está unificado en 10.0.11. **No hay skew en runtime PassPlat.**
- **Skew real**: solo persiste en builds standalone de CBP (`Synchronous`/`Services.Sync` assets = 10.0.9) y en InventaNet (10.0.8 por sus propias refs).
- **Riesgo de mezcla de vías en un proceso**: bajo para PassPlat (no carga el stack sync en producción), pero **relevante para el framework**: cualquier consumidor futuro que referencie BOTH stacks a la vez queda expuesto a las dos AssemblyVer (10.0.9 y 10.0.11) para `Microsoft.EntityFrameworkCore.Relational`.

## 8. Riesgo y recomendación (neutral, para decisión S29.1)

| Opción | Descripción | Valoración objetiva |
|---|---|---|
| **A — Unificar Sync → objetivo (10.0.11)** | Bump `CBP.Data.Synchronous.csproj` (Relational 10.0.9→10.0.11) + `CBP.Services.Sync` (transitiva se autocorrige). | Elimina skew en CBP; alinea con runtime PassPlat; sin breaking changes (patch lane). Afecta a `InventaNet` (compila contra 10.0.11 en su `Inventa.Data` al restaurar; sus refs directas propias siguen en 10.0.8). |
| **B — RETAIN 10.0.9 justificado** | Dejar Sync en 10.0.9, documentando limitación. | Conserva skew; InventaNet ya está en 10.0.8 (< 10.0.9), por lo que el "beneficio" de quedar en 10.0.9 no cubre a InventaNet; mantiene deuda innecesaria. |
| **C — Central Package Management** | Introducir `Directory.Packages.props` en CBP para fijar una versión única. | Ortogonal al bump; no elimina el skew por sí solo (requiere además alinear las versiones en el props), pero la previene a futuro. |
| **D — Parcial/familia regresión** | Solo alinear el par `CBP.Data.Synchronous`+`CBP.Services.Sync` sin tocar el resto. | Es equivalente a A (son los 2 únicos productores en skew). D no aporta diseño adicional salvo alcance mínimo. |

**Recomendación neutral**: la evidencia favorece **A** (unificar a 10.0.11) como objetivo, con **C** (CPM) como hardening estructural opcional en un sprint de framework posterior. No implica decisión — se eleva a S29.1 para aprobación formal con autorización explícita antes de tocar CBP.
