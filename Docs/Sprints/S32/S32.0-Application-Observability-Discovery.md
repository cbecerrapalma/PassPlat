## 1. Executive Summary

S32.0 investiga las dos deudas de observabilidad de la capa de aplicación priorizadas en S30.0:

- **DEUDA-009** (P1): 4-5 bloques silenciosos en `DispConfiableService` que tragan fallos de auditoría y de publicación de eventos sin log.
- **DEUDA-008** (P2): reflexión heurística en `BackgroundStatusService` para derivar el estado de los jobs en el Dashboard Operacional.

**Resultados clave**:

1. **DEUDA-009 — los 5 bloques silenciosos son reales y clasificables en 2 familias**:
   - **Publicación de eventos** (`catch { }` en `RevocarConfianzaAsync`) → es la **excepción silenciada** (clase F). El patrón de referencia correcto ya existe en el propio proyecto: `IPService.VerificarCambioIPAsync` (L175–215) emite `Event_Failed` + `Exception` + `correlationId` en el mismo escenario.
   - **Auditoría** (`if (auditResult.IsFailure) { }` y `catch { }` en Revocar/Eliminar/Bloquear) → **Result.Failure excepción silenciada** (clase E/F). Silencian el fallo de `RegistrarAuditoria`, rompiendo el contrato de auditoría sin rastro.
   - Hallazgo adicional de Discovery: **5º bloque** en `DetectarNuevoDispositivoAsync` (L180–186, `catch { }` sobre `PublishAsync` del `NewDeviceDetectedEvent`) **no estaba inventariado** en S30.0 (solo 4).

2. **DEUDA-008 — la reflexión es completamente inservible por diseño**:
   - **Ninguno** de los 5 jobs (`EmailBackgroundService`, `IdenExtTokensRotacionJob`, `OutboxProcessor`, `SesionCleanupService`, `PasswordExpirationBackgroundService`) declara `_running`, `_isRunning` ni `IsRunning` (grep: **0 matches**). La reflexión cae **siempre** al fallback `return true` (L83).
   - Consecuencia: el Dashboard Operacional informa **"Activo" permanente** para todos los jobs, con `UltimaEjecucion = null` y `ItemsProcesados = 0` fijos (L47–49). **Estado falso por construcción — dato desinformativo**.

3. **Dos violaciones de contrato de logging descubiertas** (fuera del alcance primario, registradas como hallazgos adicionales: V-01 y V-02).

4. **Cero cambios necesarios en CBP**: toda la solución vive en `PassPlat.Aplicacion`. No se aplica STOP por este Discovery.

5. **Recomendación de diseño**: DEUDA-009 → **Opción A** (logging + continuar) con el vocabulario `Event_Failed`/`LoggingEvents` ya certificado; DEUDA-008 → **Opción B** (`IBackgroundJobStatus`, nuevo contrato en PassPlat sobre el estado real de los jobs, sin tocar CBP).

**Conclusión**: S32.0 = ✅ DISCOVERY COMPLETE. `S32.1` (Diseño) y `S32.2` (Implementación) **NO AUTORIZADOS**. No se ha modificado ni un carácter de código.

### 5.2 Taxonomía de clasificación A–F (aplicada)

Definición para S32.0 (heredera de la clasificación A/B/C/D de S31.0, extendida a manejo de errores):

| Clase | Significado | Tratamiento esperado |
|-------|-------------|----------------------|
| **A** | Operación principal — el fallo debe ser observable y propagarse | `Result.Failure` |
| **B** | Operación secundaria funcional — fallo = falla la operación | `Result.Failure` |
| **C** | Best-effort crítica (auditoría/evento) — fallo logueado y continuar | Log `Error`/`Event_Failed` + continuar |
| **D** | Best-effort no crítica — loguear y continuar | Log `Warning` + continuar |
| **E** | `Result.Failure` silenciado — al menos log | Log de nivel acorde al impacto |
| **F** | Excepción silenciada — al menos log `Event_Failed` | Log + continuar |

**Resultado DEUDA-009**: 4 bloques son **F**, 1 es **E**. **Ninguno es legítimo.** Todos pierden observabilidad (Event_Failed) y trazabilidad de auditoría.

### 5.3 Contraste con el patrón de referencia (IPService)

`IPService.VerificarCambioIPAsync` (L175–215) muestra exactamente cómo **deben** manejarse los fallos de publicación de eventos de seguridad en la misma capa:

```
try
{
    var publishResult = await _eventPublisher.PublishAsync(evt, ct);
    if (publishResult.IsFailure)
        _olog.LogError(new LogEvent { EventName = LoggingEvents.EventFailed, Scope = LoggingScopes.DomainEvents,
            Message = "Fallo al publicar SecurityAlert", Args = [...], Exception = null,
            Properties = { category, operation=Publish, correlationId, userId, tenantId, ip } });
}
catch (Exception ex)
{
    _olog.LogError(new LogEvent { EventName = LoggingEvents.EventFailed, ..., Exception = ex, ... });
}
```

Ese patrón es **idéntico** al caso DEUDA-009 #1/#5. `IPService` ya inyecta `ILoggerService _olog`; `DispConfiableService` **no** lo inyecta — primera acción del diseño S32.1.

| Método | Endpoint | Impacto si falla el bloqueo |
|--------|----------|------------------------------|

### 15.1 Decisión abierta de diseño (a resolver en S32.1 DESIGN)

**Semántica del contrato `IBackgroundJobStatus`**: ¿representa **jobs ejecutables** (solo `BackgroundService`) o **fuentes de estado operativo** (incluye colas/componentes que informan estado, p. ej. `EmailQueue`)?

Contexto de la objeción del usuario:
- `EmailQueue` **no es** un `BackgroundService` (es infraestructura de encolado, singleton `IEmailQueue`).
- `BackgroundStatusService` hoy lo añade manualmente con `ItemsProcesados = _queue.Pending` (L53–59).
- Incluirlo en el mismo contrato que los 5 jobs puede crear una **abstracción demasiado amplia** que mezcle "unidad de ejecución en background" con "origen de métrica operativa".

Opciones a evaluar en S32.1 DESIGN (sin elección automática):
- **B1**: Contrato estricto de job ejecutable (5 `BackgroundService`) — `EmailQueue` se reporta como fuente aparte o se incorpora una interfaz menor dedicada.
- **B2**: Contrato de estado operativo amplio (5 jobs + `EmailQueue`) — `IBackgroundJobStatus` expone `Nombre`, `Running`, `UltimaEjecucion`, `ItemsProcesados`.
- **B3**: Dos contratos (job status + fuente operativa), donde `EmailQueue` implementa solo el segundo.

La elección debe basarse en evidencia de consumo real del DTO (quién consume `EmailQueue.Pending` en el Dashboard y con qué expectativa), no por preferencia de diseño.
