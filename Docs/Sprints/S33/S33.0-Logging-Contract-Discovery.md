## 3. Hallazgos

### H1 — Único literal libre en todo PassPlat: `IPService.cs:135`

Confirmado con grep exhaustivo (`.cs`, todos los directorios funcionales): el **único** `EventName = "literal"` libre en todo el árbol PassPlat es:

```csharp
// PassPlat.Aplicacion/Services/SPro/DispConfiableService.cs → NO
// PassPlat.Aplicacion/Services/BBDD/IPService.cs:135 → SÍ
EventName = "Event_Queued",
```

- Contexto completo (L89–150 `DetectarNuevaIPConOutboxAsync`): se emite cuando la IP es **nueva** y se prepara el Outbox (`Outbox.Crear("NewIpDetectedEvent", ...)`).
- Todos los demás emisores verificados usan constantes del catálogo:
  - `PoliticaPwdRepository` → `EmitCacheEvent(LoggingEvents.CacheHit, ...)` ✅
  - `AppRepository` → `LoggingEvents.Cache*` ✅ (grep)
  - `ConfigTenantRepository` → `LoggingEvents.Cache*` ✅
  - `AuthService`, `PasswordService`, `BloqueoService`, `EmailQueue` → constantes `LoggingEvents.*` ✅
  - `OutboxProcessor` (`EmitBgLog` L53) → recibe `eventName` como parámetro, invocado con constantes `LoggingEvents.BackgroundJob*` ✅
- **Verdicto**: V-02 es el único literal libre en PassPlat.

### H2 — CBP framework sin literales libres

Grep en árbol CBP de todos los valores de eventos (`"Event_Queued"|"Event_Published"|"Event_Handled"|"Event_Failed"|"Email_Queued"|"Login_Succeeded"|"Background_Job`):

- 8 matches, **todos** en `CBP.Core/CBP/Logging/LoggingEvents.cs` (definiciones de constantes) ✅
- `EventDispatcher.cs` (CBP.Events): emite `LoggingEvents.EventPublished` (L313), `EventHandled` (L334), `EventFailed` (L351/373) — **sin literales** ✅
- `JwtTokenService.cs`: `LoggingEvents.JwtValidated`/`JwtExpired` — sin literales ✅
- `EmailQueue` (PassPlat): `LoggingEvents.EmailQueued` ✅

**Verdicto**: CBP no contiene literales de eventos. El framework emite exclusivamente vía catálogo.

### H3 — El catálogo NO cubre todos los eventos vivos (gap `Event_Queued`)

`LoggingEvents.cs` (CBP.Core, 52 líneas) — inventario completo:

| Sección | Constantes |
|---------|-----------|

| Data | `Sql_SlowQuery` |

**`Event_Queued` NO existe** como constante (gap confirmado). El valor textual `"Event_Queued"` solo vive en `IPService.cs:135`.

**Regla de gobernanza violada** (EventCatalog.md L14–16): *"cualquier `EventName` usado en el código DEBE estar registrado... un evento que aparezca en el código y no en este catálogo es una violación de contrato."*

### H4 — Diseño recomendado No-BREAKING (cambio aditivo compatible)

- La cadena certificada S21/S22/S25.2 documenta: `Event_Queued → Event_Published → Email_Queued → Event_Handled → Email_Sent`.
- Añadir `public const string EventQueued = "Event_Queued";` en `LoggingEvents.cs` (sección Domain Events) es un cambio **aditivo** con el **mismo valor textual** → 0 breaking en logs, consultas históricas, dashboards ni tests.
- Migrar `IPService.cs:135` de literal a `LoggingEvents.EventQueued` produce el **mismo string en runtime** → las cadenas certificadas S21/S22 permanecen textualmente idénticas.

### H5 — Ningún test depende del literal `Event_Queued`

- **xUnit (PassPlat)**: grep `"Event_Queued"` en `.cs` → 1 match total (el propio emisor). Ningún test fija el literal.
- **Playwright**: `tests/fase16/*.spec.ts` verifican `eventName` con `toBe('Cache_Miss')`, `toBe('Email_Queued')`, `toBe('Logout')`, `toBe('Email_Sent')`, `toBe('Cache_Invalidation')` — **ninguno** referencia `Event_Queued`.
- **CBP**: 0 matches.

**Verdicto**: renombrar/migrar a constante NO rompe ningún test ni consulta.

## 6. Análisis semántico de naming

- El valor `"Event_Queued"` sigue el patrón de naming del grupo Domain Events: `Event_Published`, `Event_Handled`, `Event_Failed` — todos `Event_*` con underscore. Es **consistente** con el grupo.
- La constante propuesta (`EventQueued`) sigue el patrón de constantes: `EventPublished`, `EventHandled`, `EventFailed` → `EventQueued`. Y el emisor gemelo `Email_Queued` ya existe como constante (`EmailQueued`).
- **No hay inconsistencia de naming**: el único defecto es el **registro** (falta constante + falta fila catálogo), no el nombre.
