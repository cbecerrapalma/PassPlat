## 4. Arquitectura de emisión — dos canales disjuntos

```
┌─ CANAL 1 (EF pipeline) ─────────────────────────────────────────────┐
│ LINQ / SaveChanges / ExecuteSqlRawAsync → DbCommandInterceptor      │
│   → SqlSlowQueryInterceptor (CBP.Data.Utilities)                    │
│   → si Duration >= threshold → ILoggerService.Log*(LogEvent)        │
└──────────────────────────────────────────────────────────────────────┘
┌─ CANAL 2 (RawQuery ADO) ────────────────────────────────────────────┐
│ QuerySPAsync / ExecuteSP* → SqlCommand + ExecuteReader/NonQuery/    │
│   ExecuteScalar → RawQueryRepository{Async,Sync} (Stopwatch)        │
│   → si duration >= threshold → ILoggerService.Log*(LogEvent)        │
└──────────────────────────────────────────────────────────────────────┘
   → correlación garantizada por enrichers CBP.Logging (S16.4)
   → background jobs: correlationId null legítimo (sin HttpContext)
```

**H1 (canales disjuntos, S37.0)**: el interceptor EF captura solo comandos emitidos por el pipeline EF (LINQ, SaveChanges, ExecuteSqlRaw). `RawQueryRepository*` ejecuta ADO directo con `SqlCommand` sobre `GetDbConnection()` → **no** pasa por interceptor EF. Un comando nunca atraviesa ambos canales → sin doble medición estructural.

## 5. Componentes de diseño

### 5.1 `SqlSlowQueryInterceptor : DbCommandInterceptor` (NUEVO, `CBP.Data.Utilities/Services/`)

- **Overrides instrumentados** (medición oficial EF `CommandExecutedEventData.Duration`):
  - `ReaderExecuted` + `ReaderExecutedAsync`
  - `NonQueryExecuted` + `NonQueryExecutedAsync`
  - `ScalarExecuted` + `ScalarExecutedAsync`
- **Ctor**: `SqlSlowQueryInterceptor(ILoggerService logger, IOptions<LoggingOptions> options)`.
- **Umbral**: `options.Value.SqlSlowQueryThresholdMs` (D-10). `Duration.TotalMilliseconds < threshold` → early-return (overhead ~1ns).
- **Filtro opcional por CommandSource**: `LinqQuery/SaveChanges/ExecuteSqlRaw/FromSqlQuery` → mapeo a `commandType` lowerCamel (D-08).
- **Metadata emitida** (solo segura):
  - `eventName` = `LoggingEvents.SqlSlowQuery` · `scope` = `LoggingScopes.Sql` · `category` = `LoggingCategories.DataSql`
  - `elapsedMs` = `Math.Round(Duration.TotalMilliseconds, 1)`
  - `operation` = `LoggingOperations.Execute`
  - `source` = `LoggingSources.SqlServer`
  - `commandType` = mapeo del `CommandSource` (ej `"linqQuery"`, `"saveChanges"`, `"executeSqlRaw"`)
  - `procedureName` / `commandName` = primer token del `CommandText` **sanitizado** (STOP: solo prefix alfanumérico + `_`; truncado 128 chars; jamás valores tras `=`).
- **NUNCA**: parámetros (`Command.Parameters`), sentencia completa, valores literales, `EnableSensitiveDataLogging` heredado.

### 5.2 Instrumentación RawQuery ADO (Async y Sync)

- **Archivos**: `RawQueryRepositoryAsync.cs`, `RawQueryRepositorySync.cs` (ambos `internal sealed`).
- **Ctor nuevo opcional**: `RawQueryRepository(DbContext context, ILoggerService? logger = null, IOptions<LoggingOptions>? options = null)` — mantiene el ctor actual (`context`) como legado (lazy-init sin métricas). Comportamiento anterior **no cambia** si logger es null.
- **Puntos de medición** (mismas firmas, nada re-nombrado):
  - Async: `ExecuteReaderAsync` (y variante), `ExecuteNonQueryAsync`, `ExecuteScalarAsync`.
  - Sync: `ExecuteReader`, `ExecuteNonQuery`, `ExecuteScalar`.
  - Patrón: `var sw = Stopwatch.StartNew(); ... try/finally { if (logger is not null && runner) EmitIfSlow(sw.Elapsed, cmd); }`, replicando la estructura `try-catch` actual (código DB_ERROR intacto).
- **Metadata**: `operation=Execute`, `commandType="storedProcedure"`, `source=SqlServer`, `procedureName`/`commandName` = `CommandText` (nombre del SP) sanitizado. `elapsedMs` real. Sin `@parametros`.
- **Paridad D-13**: misas reglas y estructura en Async y Sync — no clonación mecánica (S25), pero sí **espejo funcional 1:1**.

### 5.3 Plomería DI

- **`UnitOfWorkAsync` / `UnitOfWorkSync`**: ctor `internal` gana parámetros opcionales `ILoggerService? logger = null, IOptions<LoggingOptions>? options = null`; el lazy-init `new RawQueryRepositoryAsync(_context, _logger, _options)` (hoy `UnitOfWorkAsync.cs:41-45`) lo propaga.
- **Factories** (`AsynchronousServiceCollectionExtensions.AddUnitOfWorkAsync<TDbContext>` :24-27 y sync `:24-27`): resuelven opcionalmente `sp.GetService<ILoggerService>()` y `sp.GetService<IOptions<LoggingOptions>>()`. Ctor es `internal` → **sin cambio de contrato público**.
- **`UtilitiesServiceCollectionExtensions`**: `AddSqlSlowQueryInterceptor(ServiceLifetime lifetime = ServiceLifetime.Singleton)` siguiendo el patrón exacto de `AddAuditingInterceptor` (`:14-23`) — se registra el interceptor, y **el consumidor** lo añade con `AddInterceptors(...)` en su `AddDbContext`.
- **PassPlat `Program.cs:133-142`**: `options.AddInterceptors(sp.GetRequiredService<SqlSlowQueryInterceptor>())` en el bloque `AddDbContext` actual (hoy no usa interceptores); previo `builder.Services.AddSqlSlowQueryInterceptor()`.

## 6. Configuración — única fuente (reconciliación de clave)

**Hallazgo F-6.1 (S37.0)**: `LoggingOptions` se enlaza desde la sección **`"Cbp:Logging"`** (`CBP.Logging/ServiceCollectionExtensions.cs:36` → `services.Configure<LoggingOptions>(configuration.GetSection("Cbp:Logging"))`), NO desde `"Logging"`.

**Consecuencia de diseño**: el usuario propuso `Logging:SqlSlowQueryThresholdMs`, pero la fuente única real del framework es `Cbp:Logging`. La propiedad nueva `SqlSlowQueryThresholdMs` debe vivir en `LoggingOptions` y el key efectivo será `Cbp:Logging:SqlSlowQueryThresholdMs`:

```json
"Cbp": { "Logging": { "EnrichWithHttpContext": true, ..., "SqlSlowQueryThresholdMs": 250 } }
```

> ⚠️ **POL: clave de configuración pendiente de confirmación del usuario** (sección propuesta en S37.0 `Logging:` vs sección ligada real `Cbp:Logging`). El diseño propone respetar la ligadura real (`Cbp:Logging`) porque:
> 1. Es la sección que `Configure<LoggingOptions>` ya lee — cero costo nuevo.
> 2. Única fuente de verdad para ambos canales.
> 3. Evita una segunda sección `Logging` paralela (violaría 'single source').
