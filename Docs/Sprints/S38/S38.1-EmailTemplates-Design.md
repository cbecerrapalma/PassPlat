## 2. Decisión D1 — Contrato de variables (fuente única)

**Regla general**: el contrato es el conjunto de **placeholders declarados por el template** (`{{...}}` en asunto + cuerpo, o en `VariablesDoc`). El emisor DEBE entregar esos placeholders. Las variables extra que entregue un emisor y que no estén declaradas por el template son opcionales y libres (no forman parte del contrato).

### Tabla única template → placeholders → variables entregadas → fuente → estado actual

| Template | Placeholders declarados (BD) | Variables entregadas hoy (emisor) | Fuente | Estado contrato |
|----------|------------------------------|-----------------------------------|--------|-----------------|
| **3 mfa-code** | `{{MfaCode}}`, `{{ExpiraMinutos}}` (cuerpo) | job: `MfaCode` (Extra L482) + motor `UserName/FechaHora`; ruta directa `SendMfaCodeAsync`: `UserName/MfaCode/ExpiraMinutos=5` | `MfaCode` = `_rng.Next` con `cfg.LongitudCodigoMFA`; `ExpiraMinutos` = `cfg.TiempoValidezCodigoMFA` (minutos — misma fuente que `MfaCodeStore.StoreAsync` L477; **ruta directa hardcodea 5**, ruta job **no lo aporta**) | ❌ **incompleto**: ruta job no entrega `ExpiraMinutos`; ruta directa inconsistente con `cfg` |
| **11 password-expired** | `{{AppName}}` (asunto); cuerpo estático | `DiasRestantes/FechaExpira/TipoEvento/TemplateCode/AppName` (job L294-307 y trigger L117-130) + motor | `AppName` = constante `"PassPlat"` (`AppName="PassPlat"` en emisor) | ✅ completo |
| **12 first-login** | `{{AppName}}` (asunto); cuerpo estático | PasswordService (`PrimerUso`, L317-325): **sin vars Extra**; trigger L145-155: solo `IdUsuario/IdTenant` | `AppName` = **NO entregada hoy** → asunto con placeholder vacío | ❌ **faltante**: `{{AppName}}` |
| **15 new-device** | `{{AppName}}` (asunto) + `{{Dispositivo}}`, `{{IP}}`, `{{FechaHora}}` (cuerpo) | `NombreDispositivo/TipoDispositivo/Fabricante/Modelo/IpAddress/UserAgent/FechaDeteccion` (handler L21-33) + motor `UserName/FechaHora` | `Dispositivo` ← `NombreDispositivo` (a definir mapeo); `IP` ← `IpAddress`; `AppName` = `"PassPlat"` | ❌ **mismatch**: template `Dispositivo/IP` vs emisor `NombreDispositivo/IpAddress` + asunto `{{AppName}}` **no entregado** |
| **16 new-ip** | `{{AppName}}` (asunto) + `{{IP}}`, `{{FechaHora}}` (cuerpo) | `DireccionIP/Pais/Ciudad/UserAgent/DeviceName/FechaDeteccion` (handler L21-32) + motor `UserName/FechaHora` | `IP` ← `DireccionIP`; `AppName` = `"PassPlat"`; `FechaHora` ✓ (motor) | ❌ **mismatch parcial**: template `IP` vs emisor `DireccionIP`; asunto `{{AppName}}` **no entregado** (handler no manda `AppName`) |

> ⚠ **Corrección a S38.0 (S38.1)**: los templates **15 y 16** declaran `{{AppName}}` en el asunto (`'Nuevo dispositivo - {{AppName}}'` / `'Nueva IP - {{AppName}}'`) y **ninguno de los dos handlers lo entrega** → asuntos actuales con `AppName` vacío (incluye los 10 envíos S21/S22 de new-ip). `VariablesDoc` NO refleja `AppName` (solo `UserName/FechaHora/Dispositivo/IP`) → **la fuente de verdad de placeholders es el render (asunto + cuerpo), NO `VariablesDoc`**.

### 2.1 Computación del motor (aplica a todas las rutas con `EmailJob`)

`SendFromTemplateWithJobAsync` (PassPlatEmailService.cs:248-254) enriquece SIEMPRE dos variables:
- `UserName` (job.UserName, o resuelto por IdUsuario)
- `FechaHora` (`DateTime.Now.ToString("yyyy-MM-dd HH:mm:ss")`)

Luego añade `job.Extra`. Por tanto: **todo template que declare `{{UserName}}` o `{{FechaHora}}` queda satisfecho automáticamente en rutas con `EmailJob`**, sin intervención del emisor. (Rutas directas tipo `SendMfaCodeAsync` construyen sus vars explícitamente.)

## 3. Decisión D2 — Fuente de verdad: el template (Opción A)

Se adopta la **Opción A**: el **template es la fuente de verdad** (interfaz de presentación) y **el emisor debe adaptarse a sus placeholders**. Queda prohibido en S38.2:
- Renombrar placeholders de templates, renombrar templates, o alterar cuerpos para "encajar" con el código actual.
- Cambiar el significado semántico de una variable (ej. usar `FechaHora` para otra cosa distinta).

Transformaciones permitidas (único caso): **mapeo equivalente** emisor→template documentado en D1 (columna "Fuente"), p. ej. `IP ← DireccionIP` cuando `DireccionIP` es precisamente la IP de origen. No se permite coacción de tipos de fecha/string fuera de las ya usadas por el motor.

## 5. Decisión D4 — Estrategia de certificación

### 5.1 Tres niveles de evidencia (obligatorios para los 4 pendientes)

Para `mfa-code`, `password-expired`, `first-login`, `new-device` la certificación deberá demostrar la cadena completa (no basta `Enqueue`):

```
trigger real → EmailJob → template → render → SMTP → EmailLog.Estado → TrackingId → destinatario → correlationId
```

### 5.2 Gate de certificación por template (contenido + pipeline)

| # | Criterio | Fallo si... |
|---|----------|-------------|
| C-1 | trigger/HTTP responde OK (2xx) que encola EmailJob | 4xx/5xx o job no encolado |
| C-2 | `EmailLog.Estado = 'enviado'` | 'pendiente'/'fallido' |
| C-3 | `EmailLog.MsgIdExterno ≠ null` (TrackingId MailKit) | null |
| C-4 | `EmailLog.IdTemplate = id del template esperado` (3, 11, 12, 15; para 11 confirmar TemplateCode→template usado) | id erróneo |
| C-5 | `subject` renderizado **sin** `{{...}}` sin resolver | contiene `{{` |
| C-6 | `body` renderizado **sin** `{{...}}` sin resolver | contiene `{{` |
| C-7 | `EmailLog.CorrelationId` presente y coherente con el trigger | null |
| C-8 | Destinatario correcto (email del usuario) | destinatario vacío/erróneo |

**Regla**: un placeholder que Fluid convierte en vacío es **fallo de calidad funcional** (C-5/C-6), aunque el envío SMTP sea exitoso. No se declara certificado un template con C-5/C-6 rojos.

### 5.3 Disparadores reales por template (fuente reproducibilidad)

| Template | Disparador | Precondición (setup) |
|----------|------------|----------------------|
| 3 mfa-code | Login con `requiereMFA` true y método principal **Email (3)** | Usuario con registro MFA IdTipoMFA=3, `EsPrincipal=1`, `IdEstado=1` + Email configurado. **Hoy BD tiene MFA vacía** → requerirá registrar método Email (SQL/UI) durante la campaña |
| 11 password-expired | `POST /api/password/trigger-expiration` (JWT) | Usuario con historial + `FecExpira` calculado (días 15/7/3/1/0) |
| 12 first-login | `POST /api/password/trigger-first-login` (JWT), o cambio con `IdTipoCambio=PrimerUso` | usuario autenticado |
| 15 new-device | Login con `idDisp` nuevo/no confiable (inline en `DetectarCambiosEnLoginAsync`) | registrar dispositivo nuevo para el usuario en la campaña |

`new-ip` (16): **sin nueva campaña** — S38.0 recuperó evidencia real (10 envíos, EmailLog 20-29, TrackingId + correlationId W3C, chain Outbox certificada S21/S22). Solo se aplicará el fix F-3 y se verificará el contenido del próximo envío real.

### 5.4 Criterio de cierre S38.2

- Fixes F-1..F-4 aplicados + build 0 errores.
- Campaña de certificación: gates C-1..C-8 **todos PASS** para `mfa-code`, `password-expired`, `first-login`, `new-device`.
- `new-ip` re-verificado por contenido en el siguiente trigger real (C-5/C-6) sin campaña nueva.
- Documento de certificación S38.2.
