## Evidencia — cadena de CorrelationId

### Pipeline del EmailJob (independiente del origen)

```
call-site (Controller/Servicio/Handler)
  → new EmailJob(..., CorrelationId: X)     ← X = null | Guid.NewGuid() | @event.CorrelationId
  → EmailQueue.EnqueueAsync(job)
        ├── var correlationId = job.CorrelationId ?? HttpContext.Items[HttpCorrelationIdKey]   ← SOLO para el log
        └── await _channel.Writer.WriteAsync(job)                                              ← job CONSERVA CorrelationId=null
  → EmailBackgroundService.ProcessQueueAsync → scope → IPassPlatEmailService.SendFromJobAsync(job)
  → PassPlatEmailService.SendEmailAsync(..., job.CorrelationId, ...) → CreateOrUpdateLogAsync
  → EmailLog.Crear(..., correlationId, ...) → EmailLog.CorrelationId ← PERSISTE lo que traía el job
```

**Punto de falla**: `EmailQueue.EnqueueAsync` (L105-125) calcula `correlationId` (L107-108) pero solo lo usa en la propiedad log (L120). El `job` escrito al channel (L110) mantiene su `CorrelationId` original. El EmailLog lo persiste `PassPlatEmailService.CreateOrUpdateLogAsync` → `EmailLog.Crear` (Dominio L30, L41). No hay re-escritura del job con el correlationId del HttpContext.

### Cómo se genera el correlationId del request

`CorrelationIdMiddleware` (WebAPI/Middleware/CorrelationIdMiddleware.cs L21-50):
1. Header entrante `X-Correlation-ID` si existe → usa ese valor.
2. Si no: `Activity.Current?.Id` (W3C traceparent) o `context.TraceIdentifier` o `Guid`.
3. Guarda en `context.Items[LoggingPropertyNames.HttpCorrelationIdKey]` (L24) y en response header.

Los flujos login/MFA pasan por este middleware con `Activity` W3C activo → el correlationId del request es W3C. Los handlers de eventos lo propagan vía `@event.CorrelationId` (asignado con `WithCorrelationId` desde `HttpContext.Items`). Los triggers de PasswordController NO lo leen.

## Causa raíz

**`PasswordController` TriggerExpiration (L117-130) y TriggerFirstLogin (L145-156) construyen `EmailJob` sin el parámetro `CorrelationId`.** El `EmailQueue.EnqueueAsync` no compensa (H2 desmentida): el fallback C-2 solo enriquece la propiedad del evento log `Email_Queued`, no el job persistido. Resultado: `EmailLog.CorrelationId = NULL` en EmailLog 35/36.

Los flujos correctos (MFA, new-device, new-ip) lo demuestran: el correlationId viaja **dentro del job** (explícito) hasta la persistencia. Los triggers son los únicos endpoints administrativos que rompen la cadena.

## Alternativas para S39.1 Design (a decidir por el usuario)

### Opción A — Mínima: pasar correlationId explícito en los 2 triggers
Cambiar solo `PasswordController` para inyectar el correlationId del HttpContext en el `EmailJob`:
```csharp
var correlationId = HttpContext.Items[LoggingPropertyNames.HttpCorrelationIdKey] as string;
// new EmailJob(..., CorrelationId: correlationId)
```
- ✅ Alcance exacto S39 (2 endpoints), cero riesgo de regresión
- ✅ Alineado con patrón existente `UsuariosController.cs:255`
- ⚠️ No corrige el patrón general (otros call-sites sin correlationId siguen NULL)

### Opción B — Transversal: re-escribir el job en `EmailQueue.EnqueueAsync`
Mover el fallback a la escritura del job:
```csharp
job = job with { CorrelationId = job.CorrelationId ?? _httpContextAccessor.HttpContext?.Items[...] as string };
await _channel.Writer.WriteAsync(job, ct);
```
- ✅ Corrige TODOS los call-sites que omiten correlationId (incluidos los 2 triggers) sin tocarlos uno a uno
- ✅ Contrato S16.4 correcto: el job SIEMPRE hereda el correlationId del request cuando el call-site no lo especifica
- ✅ Call-sites que pasan explícito (`@event.CorrelationId`, retry) conservan precedencia
- ⚠️ Riesgo: `EmailBackgroundService` es singleton y también lee del channel; en flujos sin HttpContext (background/polling) `HttpContextAccessor` devuelve null → job queda null (correcto: no hay request)
- ⚠️ Cambio fuera del alcance literal "2 endpoints" — requiere aprobación del usuario

### Recomendación
**Opción A** para respetar el alcance S39 aprobado (2 endpoints, riesgo mínimo), documentando el patrón generalizado como hallazgo para un sprint de consolidación posterior. Si el usuario prefiere resolver el contrato de raíz con 1 línea, **Opción B**.
