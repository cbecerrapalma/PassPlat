## Contrato de cambio (Opción A)

### Cambio conceptual (2 líneas por trigger)

```csharp
var correlationId = HttpContext.Items[LoggingPropertyNames.HttpCorrelationIdKey] as string;
// ...
await emailQueue.EnqueueAsync(new EmailJob(..., CorrelationId: correlationId), ct);
```

### Cadena final esperada

```
HTTP Request (con o sin X-Correlation-ID)
  ↓
CorrelationIdMiddleware → context.Items[HttpCorrelationIdKey]
  ↓
PasswordController.Trigger{FirstLogin|Expiration} → EmailJob.CorrelationId = correlationId
  ↓
EmailQueue.EnqueueAsync (SIN CAMBIOS — fallback C-2 intacto)
  ↓
EmailBackgroundService → IPassPlatEmailService.SendFromJobAsync
  ↓
PassPlatEmailService → EmailLog.Crear(..., correlationId, ...)
  ↓
EmailLog.CorrelationId = valor del header/request
```

### Fuente del correlationId (ordinalidad del middleware, ya certificado)

`CorrelationIdMiddleware.GetOrCreateCorrelationId`:
1. Header entrante `X-Correlation-ID` si existe → se usa ese valor (persiste tal cual).
2. Si no: `Activity.Current?.Id` (W3C) / `context.TraceIdentifier` / Guid.
3. Siempre guarda en `context.Items[LoggingPropertyNames.HttpCorrelationIdKey]`.

**Gate clave**: el valor del header `X-Correlation-ID` enviado debe llegar **exactamente igual** a `EmailLog.CorrelationId` (no basta con "no null").

## Deuda registrada (fuera de S39)

### H-3 — CorrelationId local en EmailJob de operaciones de seguridad (NUEVA)
- Call-sites: `AuthService.cs:478` (MfaCode), `AuthService.cs:583` (AccountLocked), `AuthService.cs:616` (SecurityAlert).
- Semántica: `Guid.NewGuid()` genera un correlationId **local**, desvinculado del request que originó la operación.
- Distinto de H-1 (donde había **ausencia**): aquí existe valor pero su significado no es el correlationId W3C del request.
- Pendiente de decisión de política: "¿cuál es el correlationId oficial para operaciones iniciadas en un request que generan email posterior?" (request/W3C vs local).
- Sprint candidato: consolidación post-S39. **NO implementar en S39.**
