**call-site background (sin HttpContext) — caso B de política, NO Guid.NewGuid:**

### Análisis de contexto (hallazgo F-H3.2)

Todos los call-sites #1-13 son **request-scoped** (invocados desde controllers dentro de un HTTP request activo). Por tanto:

- **La Opción A (request correlation cuando exista) es viable para 12/13**: hay `HttpContext` activo y el patrón ya probado es leer `HttpContext.Items[LoggingPropertyNames.HttpCorrelationIdKey]` (S39). Los servicios de aplicación no inyectan `IHttpContextAccessor` hoy, pero el patrón existe (EmailQueue lo usa como fallback en `EnqueueAsync` para el log) y los controllers ya lo leen (PasswordController, UsuariosController).
- **La Opción B (correlation local cuando la operación sea interna) aplica a** `PasswordExpirationBackgroundService` (y a cualquier futuro job). Hoy deja `null`, que es el peor de los 3 mundos (ni request ni local).
- **La Opción C (jerárquico requestId+operationId)** es la más correcta técnicamente pero introduce un formato nuevo en el contrato de `EmailLog.CorrelationId` (columna `nvarchar(450)`), rompiendo la igualdad "header == EMailLog.CorrelationId" que S39.3 estableció como criterio de gate. Requeriría migración de contrato + decisión de compatibilidad.

### Veredicto preliminar

- H-3 es una deuda **real y más amplia** de lo documentado: 12 call-sites request-scoped con GUID local desvinculado + 1 background con null.
- Requiere **Design formal (política A/B/C)** antes de implementar. La opción recomendada preliminar es **A con B como excepción explícita** (policy: request → fallback local para background; nunca null).
- Riesgo de implementación: bajo-medio. Patrón ya probado en S39. Cero impacto en `AuthenticationTokenIssuer` (jti) y `ExternalAuthService` (state).
- Delega en el usuario la decisión contractual: A (requests) / B (internos) / C (jerárquico).

### Causa raíz real (hallazgo F-H2.2)

EmailLog **37** (envío real S38.2, template 13) registró `Asunto = "MFA activado - "` (placeholder vacío). El defecto está en **el call-site, no en el template**:

`MfaService.NotificarMFAAsync` (:118-142) construye el EmailJob con:
```csharp
new Dictionary<string, object?> { ["TipoAccion"] = tipoNombre }
```
**NO incluye `AppName`**. Contraste con call-sites correctos que SÍ lo incluyen: `PasswordService.cs:321` (`["AppName"] = "PassPlat"`), `UsuarioService.cs:172` (`appName` desde ConfigApp), `IpEventHandlers.cs:26`, `DispConfiableEventHandlers.cs:26`, `PasswordExpirationBackgroundService.cs:304` (`"PassPlat"`).

Confirmado en el render: `SendFromTemplateWithJobAsync` (PassPlatEmailService:253-259) construye `vars` base (`UserName`, `FechaHora`) + `job.Extra`; `mfa-enabled` no inyecta AppName automáticamente — depende del call-site.

### Veredicto preliminar

- **H-2 NO es defecto de contenido de template. Es defecto de call-site**: falta la variable contractual `AppName` en `MfaService.NotificarMFAAsync`. El fix es 1 línea: `["AppName"] = "PassPlat"` (patrón F-1 S38.2).
- Afecta a mfa-enabled (13) y mfa-disabled (14) — ambos pasan por el mismo `NotificarMFAAsync`.
- Es una deuda **funcional trivial**, independiente de H-3, con impacto de variedad "cosmética en asunto" y riesgo de fix nulo (misma 🟢 clase de cambio que S38).
- **No tocar el template en BD** (contrato D2 S38.1: el template es fuente de verdad; si se edita el asunto se rompe el placeholder legítimo).

## PBKDF2 — deuda independiente (framework CBP)

### Estado físico (hallazgo F-P1)

Test fallido: `VerifyAsync_Pbkdf2_CorrectPassword_ReturnsTrue` — `CBP.Security.Password.Tests/PasswordHashingServiceTests.cs:72-78`. Único fallo de la suite CBP (51/52). Swap-test S36.2 §G4 probó que es preexistente e independiente del CPM.

### Causa raíz (hallazgo F-P2)

Inconsistencia hash-vs-verify en `HashingService`:

1. **Hash** (`HashPbkdf2Async`, HashingService.cs:185-220): iteraciones = `CalculateOptimalIterationsPbkdf2(pepperedPassword)` (:320-328):
   - base = `DefaultMinIterations` = **100000**
   - password de 16 chars ("TestPassword123!") ≥ 12 → `base * 0.9` = **90000**
   - `Math.Min(90000, DefaultMaxIterations=600000)` = **90000** ✅ genera con 90000.
2. **Verify** (`VerifyPbkdf2Async`, HashingService.cs:264-295): umbral hardcodeado `Pbkdf2VerifyMinIterations = 100000` (:34), con `if (iterations < Pbkdf2VerifyMinIterations ...) return false` (:285) → **90000 < 100000 → false**.

El servicio genera hashes con iteraciones por debajo de su propio umbral mínimo de verificación cuando la contraseña tiene ≥12 caracteres. **Bug de consistencia del framework CBP** (no defecto de CPM, no defecto de PassPlat).

### Impacto (hallazgo F-P3)

- **NO afecta el flujo real de PassPlat**: PassPlat usa exclusivamente **Argon2id** — `Program.cs:193` `ServiceFactory.CreateDefault()` (Algorithm default = `HashType.Argon2id`), `PassPlatPasswordSecurity.cs:35` `new HashingService()` (default Argon2id), y la entidad `HistorialPwd` fija `Algoritmo = "Argon2id"`. `HashType.Pbkdf2_SHA256` solo se activa si alguien configura explicitamente esa opción.
- **Afecta**: (a) 1 test unitario CBP (suite 51/52), (b) cualquier consumidor futuro que configure PBKDF2, (c) la credibilidad del servicio como opción soportada.
- Clasificación: **deuda del framework CBP.Securing.Cryptography**, nivel P2-P3, sin riesgo de producción hoy.

### Veredicto preliminar

- Fix correcto: alinear `CalculateOptimalIterationsPbkdf2` para que su mínimo nunca baje de `Pbkdf2VerifyMinIterations` (o que Verify use el mismo cálculo). Es cambio dentro de CBP (framework), requiere su propio Design + gates (swap-test de regresión sobre la suite CBP).
- Alternativa: si PBKDF2 no es una opción oaciada para PassPlat, documentar como RETAIN (modo no soportado) y no invertir. Decisión del usuario sobre el rol del servicio PBKDF2 en el framework.
