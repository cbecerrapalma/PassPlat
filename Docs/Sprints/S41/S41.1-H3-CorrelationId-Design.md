## Objetivo

Aplicar la **política A+B** (aprobada por el usuario):
- **A — Request correlation**: usar la correlación del request HTTP (W3C o header `X-Correlation-ID`) siempre que exista `HttpContext`.
- **B — Fallback local**: cuando no hay `HttpContext` (operación de background), generar correlación local propia.
- **Invariante**: `EmailLog.CorrelationId` **nunca null**.

## Evidencia física del pipeline (recopilada en este Design)


### Fallback actual (EmailQueue.EnqueueAsync L107-108) — DEFECTO

```csharp
var correlationId = job.CorrelationId
    ?? _httpContextAccessor.HttpContext?.Items[LoggingPropertyNames.HttpCorrelationIdKey] as string;
await _channel.Writer.WriteAsync(job, ct);   // ← escribe job ORIGINAL (no el resuelto)
```

**Dos defectos**:
1. **No persiste**: `correlationId` resuelto solo se usa en el evento de log (Properties L120); el `job` que se escribe al channel conserva su `CorrelationId` original (`null` o `Guid` del call-site). → `EmailLog.CorrelationId` llega desde `job.CorrelationId` (sin resolver) al persistedor.
2. **Precedencia**: `job.CorrelationId ?? HttpContext` — si el call-site llena un `Guid` local, ese gana sobre el request.

## Contrato de política (decisiones congeladas D1–D5)

### D1 — Único punto de resolución: `EmailQueue.EnqueueAsync`

Todo el `CorrelationId` de `EmailJob` se resuelve **en el choke point**, no en call-sites. El pipeline queda:

```csharp
public async ValueTask EnqueueAsync(EmailJob job, CancellationToken ct = default)
{
    var correlationId = job.CorrelationId
        ?? _httpContextAccessor.HttpContext?.Items[LoggingPropertyNames.HttpCorrelationIdKey] as string
        ?? Guid.NewGuid().ToString("N");   // política B: fallback local, NUNCA null

    await _channel.Writer.WriteAsync(job with { CorrelationId = correlationId }, ct);

    _olog.LogInformation(new LogEvent { /* … EventName = EmailQueued … 
        [LoggingPropertyNames.CorrelationId] = correlationId */ });
}
```

- **Precedencia deliberada**: `job.CorrelationId` explícito (eventos, S39, retry) → `HttpContext.Items` (request W3C) → `Guid` local nuevo (background). 
- **Persistencia**: `job with { CorrelationId = correlationId }` garantiza que el valor resuelto viaje al channel → a `SendFromJobAsync` → a `EmailLog.Crear`. Defecto #1 corregido.

### D2 — Limpieza de call-sites request-scoped (13 líneas de Guid)

Los 13 call-sites que llenan `Guid.NewGuid().ToString()` como `CorrelationId:` **dejan de hacerlo** (pasan `null`):
- Para que la política A (request W3C) prevalezca cuando hay `HttpContext`.
- El `Guid` local pasaba por encima del request por precedencia de `job.CorrelationId` (defecto #2).
- Archivos: AuthService (:490/591/628), PasswordService (:325/337), AccesoService (:144), UsuarioService (:178/225), BloqueoService (:147/179), MfaService (:136), TokenRestService (:79), IntentoAccesoService (:121).
- **No se tocan**: IpEventHandlers, DispConfiableEventHandlers (correlación de dominio), PasswordExpirationBackgroundService (null deliberado → B), EmailBackgroundService retry, AppService/TenantService/IdenExtService/ExternalAuthService (ya null, aprovechan fix).

### D3 — Invariante: nunca null

Tras D1+D2, ningún `EmailJob` encolado puede tener `CorrelationId = null`:
- Request: hereda W3C/header del middleware.
- Background SIN request: `Guid.NewGuid().ToString("N")` local.
- Eventos/retry: mantienen su valor explícito (nunca null por contrato del dispatcher/DB).
→ `EmailLog.CorrelationId` queda con dato siempre (rompe el patrón H-1 de `NULL`s en producción).

### D4 — No se cambia el contrato de columna ni los GUIDs no-correlation

- `EmailLog.CorrelationId` sigue siendo `nvarchar(450)`, sin migración.
- jti, OAuth state, `IdenExtTokens.CorrelationId` y `TrackingId` quedan intactos (fuera de alcance).

### D5 — Semántica de log

- El evento `Email_Queued` (scope=email, operation=queue) usa la MISMA `correlationId` resuelta (ya lo hace si se reasigna antes).
- `Event_Published`, `Event_Handled`, `Email_Sent` conservan su comportamiento certificado S21/S22/S25.2.
- `LoggingPropertyNames.HttpCorrelationIdKey` como transporte, `correlationId` como propiedad estructurada (contrato S16.4).

## Alternativas descartadas (con justificación)

| Opción | Descripción | Descartada porque |
|--------|-------------|-------------------|
| Central SIN tocar call-sites | Resolver con precedencia `HttpContext ?? job.CorrelationId` | Rompería correlación de dominio push (eventos) y S39 (controller pasa HttpContext explícito). Precedencia `job.CorrelationId ?? HttpContext` no arregla H-3 (Guid local sigue ganando). |
| Tocar solo call-sites (patrón S39) | Sustituir Guid local por `HttpContext` en cada servicio | 13 puntos de cambio sin resolver el fallback de background; deja defecto #1 (no-persistencia) intacto. |
| DI adicional en servicios | Inyectar `IHttpContextAccessor` en Auth/Password/… | Duplica lógica; el choke point ya tiene acceso. Violaría DRY y aumentaría superficie de tests. |
