## 2. Foco 1 — BUG-017.1.3 (JWT kid missing)

### 2.1 G1 — Cadena emisión → validación trazada

```
EMISIÓN  JwtTokenService.GenerateToken
         → new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_options.SecretKey))  // KeyId = ""
         → SigningCredentials(key, SecurityAlgorithms.HmacSha256)
         → header del token: {"alg":"HS256","typ":"JWT"}   ← SIN kid (confirmado G2)

VALIDACIÓN  JwtTokenService.ValidateToken
         → _validationParams: ValidateIssuerSigningKey=true, IssuerSigningKey=<misma key>
         → SIN IssuerSigningKeyResolver, SIN ConfigurationManager (key fija directa)
         → JwtSecurityTokenHandler.ValidateToken(token, tvp)
         → IDX10517 si la firma NO valida contra la única key disponible y el token no lleva kid
```

- No existe `ConfigureTokenValidation` en `Program.cs` (G3) — el TVP es el que construye `AddJwtOperator`/`JwtTokenService`.
- Emisor y validador comparten `_options.SecretKey` en la misma instancia → el desajuste solo ocurre entre instancias/configuraciones distintas.

### 2.4 G4 — Causa raíz clasificada (RECLASIFICACIÓN)

**Hipótesis previa (S40/S41)**: el bump CPM de `IdentityModel`/`JwtBearer` a 8.22.0 rompió la validación de tokens sin `kid`.

**REFUTADA empíricamente**:

1. El **mismo ejecutable 8.22.0** (proceso activo PID 19888) valida correctamente un token HS256 **sin kid**: `GET /api/apps` → **403** (autorización, no 401), y el log muestra `Jwt_Validated` + claims construidos (03:30).
2. Los **8 hits IDX10517** del bin log (03:05:59–03:06:56) corresponden a procesos **anteriores** (PIDs 8236/8408/9136), no al activo.
3. Los 3 hits del log activo a las 03:10:27 son del PID 19888 recién arrancado (03:08:08), validando tokens emitidos en el contexto de procesos previos durante la ventana de transición multi-proceso (03:01→03:08).
4. El secret (User Secrets) es estable desde junio — no hubo rotación de clave.

**Causa raíz real**: `IDX10517 "kid is missing"` es el **mensaje genérico de IdentityModel cuando la firma no valida** contra la única key disponible y el token no lleva `kid` (el matcher por kid no aplica → fallback falla). El defecto NO está en la configuración de validación de CBP (que nunca usó kid), **sino en el contexto de emisión vs. validación durante la ventana de certificación S41**: relanzamientos múltiples (8236→8408→9136→19888 en 7 minutos) donde el token emitido por una instancia fue validado por otra con distinto contexto de ejecución.

**Clasificación**: 🔵 **BUG AMBIENTAL / DE ENTORNO DE CERTIFICACIÓN** — no es un defecto de código de producción. El diseño actual (token sin kid + key única directa) es válido en IdentityModel 8.22.0.

## 4. Foco 3 — PBKDF2 soporte contractual

### 4.1 G6 — Confirmado con evidencia (tests CBP FAIL)

**Suite completa** `CBP.Security.Password.Tests` (52 tests): **51 PASS · 1 FAIL**.

```
[FAIL] VerifyAsync_Pbkdf2_CorrectPassword_ReturnsTrue   (line 77)
  Assert.True() Failure — Expected: True, Actual: False
```

**Cadena de causa** (HashingService.cs, CBP.Security.Cryptography):

1. `HashAsync("TestPassword123!")` con `HashType.Pbkdf2_SHA256` → `CalculateOptimalIterationsPbkdf2` aplica **factor 0.9** (passwords ≥ 12 chars) sobre `DefaultMinIterations = 100000` → **90000 iteraciones** → hash `$pbkdf2$...` con 90000 iter.
2. `VerifyAsync` → `VerifyPbkdf2Async` exige iteraciones en `[Pbkdf2VerifyMinIterations=100000, Pbkdf2VerifyMaxIterations=1000000]` → **90000 < 100000 → rechazado**.
3. **Contradicción interna del contrato CBP**: el generador produce hashes que el propio verificador rechaza.

**Consumidores PBKDF2**:

| Ámbito | Uso de PBKDF2 |
|--------|---------------|
| PassPlat | **0 impacto** — usa exclusivamente Argon2id (grep `HashType.|Argon2id|Pbkdf2` → solo Argon2id: `UsuarioService`, `HistorialPwd`/DB default, `Program.cs:192`, `PassPlat.Consola`) |
| CBP.Security.Password.Tests | 3 tests PBKDF2 (1 fail de verificación) |
| InventaNet / otros | Sin evidencia de hashes PBKDF2 activos |

### 4.2 Opciones (G8 Foco 3)

| Opción | Descripción | Impacto | Veredicto |
|--------|-------------|---------|-----------|
| **A — SUPPORTED** | Corregir `CalculateOptimalIterationsPbkdf2` para **no bajar de `Pbkdf2VerifyMinIterations`** (piso 100000): quitar factor 0.9/0.8 o usar `_options.Pbkdf2MinIterations` como suelo. Recupera 52/52. | CBP.Security.Cryptography + tests CBP; 0 impacto PassPlat | ✅ Recomendada (coherencia interna) |
| **B — RETAIN/DEPRECATE** | Documentar que PBKDF2 es solo **verificación legacy** (no emisión de hashes nuevos); excluir el test con justificación | 0 código; riesgo de recurrencia | Alternativa si no se quiere tocar CBP |
| **C — Cambiar constantes** | Bajar `Pbkdf2VerifyMinIterations` a 90000 | **Inseguro** (debilitaría verificación de hashes existentes de 100k) | ⛔ Descartada |

**Decisión de soporte pendiente de usuario** en S42.1 (Design): opción A vs B. La opción A es la coherente con el contrato ("cualquier hash que el framework genera debe poder verificarse") y no altera hashes existentes (solo ajusta el cálculo de iteraciones de hashes NUEVOS).
