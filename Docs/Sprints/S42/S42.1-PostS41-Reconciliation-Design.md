## Foco 1 — BUG-017.1.3 (clasificación ambiental)

### 1.1 Decisión congelada (D1)

**Clasificación formal**: 🔵 **AMBIENTAL / DE ENTORNO DE CERTIFICACIÓN** — no es deuda de código de producción.

- `CBP.Authentication.JwtBearer` **NO se modifica** (STOP condition respetada).
- Sin rotación de claves, sin `KeyId`, sin `IssuerSigningKeyResolver`.
- El diseño actual (token sin `kid` + key única directa) es **válido** en IdentityModel 8.22.0 — evidencia: proceso activo PID 19888 valida tokens HS256 sin `kid` correctamente (`Jwt_Validated`, `GET /api/apps` → 403 no 401).

### 1.2 Reproducción controlada (G1 Design — cierre de la hipótesis)

Objetivo: demostrar que **dos instancias con secretos distintos** producen exactamente el `IDX10517` observado en S41, cerrando la hipótesis de desajuste de contexto.

**Procedimiento** (S42.3 Certificación, sin modificar ningún proyecto):

| Paso | Acción | Expectativa |
|------|--------|-------------|
| 1 | Instancia A (actual, PID 19888, secret de User Secrets) sigue activa | — |
| 2 | `POST /api/auth/login/platform` en A → token T_A | 200 + JWT |
| 3 | `GET /api/apps` en A con T_A | **403** (validación OK — control) |
| 4 | Arrancar instancia B temporal en puerto alternativo (ej. 5299) con `Jwt__SecretKey` **distinto** vía env var (copia del binario, sin build) | B levanta |
| 5 | `GET /api/apps` en B con T_A | **401 IDX10517** (firma no valida contra key B + token sin kid) |
| 6 | Detener B. `GET /api/apps` en A con T_A de nuevo | 403 (sin contaminación) |

**Criterio G1 PASS**: paso 5 devuelve 401 con `IDX10517` exacto (evidencia en log de B), paso 3/6 devuelven 403. Si no se reproduce → revisar clasificación.

## Foco 3 — PBKDF2 (SUPPORTED — Opción A)

### 3.1 Decisión congelada del usuario (D3)

**Opción A — SUPPORTED**. Razón arquitectónica: el framework genera hashes que su **propio verificador rechaza**; mantener esa contradicción como comportamiento aceptado sería una mala definición de contrato, aunque PassPlat no use PBKDF2 hoy.

**Contrato congelado**:

| Aspecto | Valor |
|---------|-------|
| **Hash (generación)** | Iteraciones efectivas **>= `Pbkdf2VerifyMinIterations` (100000)** siempre |
| **Verify (verificación)** | Mantiene mínimo **100000** (`Pbkdf2VerifyMinIterations`) — sin cambios |
| **Resultado esperado** | **52/52 tests CBP** (recupera el FAIL `VerifyAsync_Pbkdf2_CorrectPassword_ReturnsTrue`) |
| **Prohibido** | ⛔ Bajar `Pbkdf2VerifyMinIterations` a 90000 — debilitaría la protección de hashes existentes y degradaría el contrato |

### 3.2 Defecto raíz (confirmado S42.0)

`HashingService.CalculateOptimalIterationsPbkdf2` (CBP.Security.Cryptography/Services/Hashing/HashingService.cs:320-328):

```csharp
private static int CalculateOptimalIterationsPbkdf2(string password)
{
    var baseIterations = Constants.Hashing.DefaultMinIterations;   // 100000

    if (password.Length >= 20) baseIterations = (int)(baseIterations * 0.8);   // → 80000
    else if (password.Length >= 12) baseIterations = (int)(baseIterations * 0.9);  // → 90000

    return Math.Min(baseIterations, Constants.Hashing.DefaultMaxIterations);
}
```

`VerifyPbkdf2Async` (L285) exige `[100000, 1000000]` → hashes de 12+ chars generados con 90000/80000 iteraciones son **rechazados por el propio framework** (FAIL test L77).

### 3.3 Implementación propuesta (S42.2)

**Archivo**: `HashingService.cs` — `CalculateOptimalIterationsPbkdf2`.

**Cambio**: aplicar un **piso** igual al mínimo de verificación, de modo que los factores 0.8/0.9 **nunca** bajen de `Pbkdf2VerifyMinIterations`:

```csharp
private static int CalculateOptimalIterationsPbkdf2(string password)
{
    var baseIterations = Constants.Hashing.DefaultMinIterations;

    if (password.Length >= 20) baseIterations = (int)(baseIterations * 0.8);
    else if (password.Length >= 12) baseIterations = (int)(baseIterations * 0.9);

    // D3: nunca por debajo del mínimo de verificación (100000)
    baseIterations = Math.Max(baseIterations, Pbkdf2VerifyMinIterations);

    return Math.Min(baseIterations, Constants.Hashing.DefaultMaxIterations);
}
```

**Resultado**:
- `password < 12` → 100000 (sin cambio).
- `12 <= len < 20` → max(90000, 100000) = **100000** (antes 90000 — el FAIL corregido).
- `len >= 20` → max(80000, 100000) = **100000** (antes 80000).
- `DefaultMaxIterations` (600000) sigue como techo — no afectado.

**Invariancia con hashes existentes**: solo cambia la generación de hashes **nuevos**; los hashes existentes de 100000 (o ≥100000) se siguen verificando igual (Verify sin cambios). No hay migración de datos.

## Alternativas descartadas (con justificación)

| Opción | Descripción | Descartada porque |
|--------|-------------|-------------------|
| Bajar `Pbkdf2VerifyMinIterations` a 90000 | Opción C S42.0 | Debilita protección de hashes existentes de 100k; degradación del contrato (rechazada explícitamente por el usuario) |
| PBKDF2 RETAIN/DEPRECATE (Opción B) | Documentar solo verificación legacy | Contradicción contractual sin resolver; framework generaría hashes que rechaza — mala definición de contrato (usuario eligió SUPPORTED) |
| Fix en `HashAsync` (no en `CalculateOptimalIterationsPbkdf2`) | Elevar iteraciones en el punto de hash | Deja el generador de iteraciones inconsistente; el piso debe estar en el cálculo central (toda llamada queda correcta) |
| Añadir `KeyId` al JWT | Resolver "kid missing" | **BREAKING**: cambia header del token → invalida tokens emitidos; STOP condition BUG-017.1.3 lo prohíbe |
| `IssuerSigningKeyResolver` en CBP | Matcher por kid | No es el fallo (key única directa valida); complejidad sin necesidad |
