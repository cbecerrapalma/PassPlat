**Ruta:** `https://localhost:7275/email-templates`  
**Páginas:** `PassPlat.Web/Pages/EmailTemplates/Index.razor` (tabla) + `EmailTemplateDialog.razor` (CRUD) + `HtmlPreviewDialog.razor` (preview)  
**Controller:** `PassPlat.WebAPI/Controllers/EmailTemplatesController.cs` (`[Authorize(Policy=EMAIL_TEMPLATES_VER/CREAR/EDITAR/ELIMINAR)]`, `BaseApiController`, `IEmailTemplateService` + `ITenantContext` + `IUnitOfWorkAsync`)  
**DTO:** `EmailTemplateDto` (`Id`, `IdTenant`, `Nombre` 100, `Cultura` 10, `Asunto` 500, `CuerpoHtml` **-1 (MAX) IsRequired**, `CuerpoTexto` -1, `Descripcion` 500, `Categoria` transaccional/marketing/sistema/alerta, `Estado` borrador/publicado/desactivado, `Version` 1, `VariablesDoc` 1000, `FecCrea=sysutcdatetime()`, `FecMod`)  
**Config:** `EmailTemplateConfiguration` — `UQ_EmailTpl_NombreCultura`, `CK_EmailTpl_Categoria/Estado`, `HasMaxLength(-1)` para `CuerpoHtml/Texto` (HTML intacto)  
**Service:** `EmailTemplateService.CrearAsync` → `EmailTemplate.Crear(...)` + `Add` + `SaveChanges`; `ActualizarAsync` → `GetByIdAsync` + `if(dto.CuerpoHtml!=null) entity.CuerpoHtml=dto.CuerpoHtml` + `FecMod=Now` + `InvalidateAllCacheAsync`; `Publicar/Desactivar` → `entity.Publicar()/Desactivar()` + `InvalidateCacheAsync`

## Editor Technology Comparison (G5)

### Opción A — BlazorMonaco 3.5.0 (Monaco)

**Fuente:** `https://www.nuget.org/packages/BlazorMonaco` — **3.5.0**, `.NET 10` (`net10.0`), `BlazorMonaco is a Blazor component wrapper for Microsoft's Monaco Editor` (VS Code powering). Context7 `/serdarciplak/blazormonaco` (449 snippets, High).

**Integración:**
```html
<script src="_content/BlazorMonaco/jsInterop.js"></script>
<script src="_content/BlazorMonaco/lib/monaco-editor/min/vs/loader.js"></script>
<script src="_content/BlazorMonaco/lib/monaco-editor/min/vs/editor/editor.main.js"></script>
```
```razor
@rendermode InteractiveServer // o InteractiveAuto para WASM
<StandaloneCodeEditor @ref="_editor" ConstructionOptions="@EditorConstructionOptions" OnDidInit="@EditorOnDidInit" />
```
- **WASM:** soporta WASM, pero `Configure Interactive Render Mode` obligatorio y `SafeInvokeAsync` + `IJSRuntime` (WASM-only overloads `Obsolete`, usar `IJSRuntime` dual). WASM requiere `static JsRuntime` en ciertos contextos, Server requiere `IJSRuntime` inyectado. Browser JS debe estar habilitado, CORS si CDN.
- **Bundle/tamaño:** Monaco `vs/editor/editor.main.js` ~2-3 MB min (vs `MudBlazor 9.8.0` actual). Impacto medible pero cacheable, `loader.js` + `jsInterop.js` adicionales. No trivial para bundle WASM, aceptable para página admin (`/email-templates` no es ruta crítica).
- **JS interop:** `jsInterop.js` bridge + `loader.js` AMD. Requiere `blazorMonaco.editor.create`. Manejar `ObjectDisposedException` vía `SafeInvokeAsync`.
- **Mantenimiento:** repo `serdarciplak/blazormonaco` activo, 3.5.0 reciente, High reputation, soporta `net10.0`. Benchmark 57.5 (moderado, no Telerik-scale).
- **Licencia:** MIT (Monaco MIT, wrapper MIT) — **gratis, sin coste**, sin dependencia Telerik/Syncfusion comercial.
- **Capacidades HTML para email:** `language: "html"`, **highlighting HTML**, **auto indentation**, **format document** (`editor.action.formatDocument`), **minimap**, **folding**, **búsqueda/reemplazo** (`Ctrl+F`), **multiline edit**, **sugerencias placeholders `{{...}}`** (via `monarchTokensProvider` custom, no built-in pero registrable).
- **MudBlazor:** compatible — Monaco es `div` + JS, no conflicto MudBlazor (ambos dentro `MudDialog`). Estilado Mud `Variant.Outlined` no aplica a Monaco (propia theme).
- **Navegación Blazor:** requiere `InteractiveServer/InteractiveAuto`; con enhanced navigation de Blazor .NET 10, Monaco debe disponer `Dispose` + `SafeInvokeAsync` para evitar `JS interop` tras `NavigationManager.NavigateTo`. Documentar antes de implementar.
- **Riesgo:** introducción de `Monaco` aumenta complejidad JS interop y bundle. No es WYSIWYG — requiere conocimiento HTML (correcto para templates).

**Veredicto A:** **Óptimo para Source Editor** — control total HTML, placeholders preservados, email-safe, gratuito MIT, .NET 10 listo. Contras: bundle, JS interop, necesita wrapper `StandaloneCodeEditor`.

### Opción B — Telerik UI for Blazor (Editor)

**Fuente:** `https://www.telerik.com/blazor-ui/editor` — `Telerik_UI_for_Blazor` (licensed), `TelerikEditor` WYSIWYG.

```razor
<TelerikEditor @bind-Value="@EditorContent" Tools="@EditorTools" />
```

- **WYSIWYG:** toolbar Bold/Italic/Underline, `insertHtml`, `ImageCommandArgs`, `TableCommandArgs`, HTML string import/export (`doc x/rtf/html/pdf` vía Document Processing).
- **Licencia/coste:** **Comercial, pago** — `Telerik UI for Blazor` license (~ $1k/dev/year), no MIT. Requiere `Telerik.Blazor` NuGet + `DocumentProcessing`.
- **MudBlazor:** **dependencia adicional paralela** — Telerik tiene su propio theme; convivir con `MudBlazor 9.8.0` implica dos design systems, potencial clash CSS (`Telerik` vs `Mud`).
- **.NET 10:** soporta .NET 10 (Telerik actualiza rápido), pero lock a vendor.
- **Placeholders:** **riesgo** — WYSIWYG normaliza HTML: puede envolver `{{AppName}}` en `<span>`, romper `{{...}}` en `&lbrace;&lbrace;`, o auto-corregir tags incompletos. Requiere modo `source` para preservar, pero WYSIWYG por defecto **transforma**.
- **Email HTML:** WYSIWYG genera markup moderno (divs, spans, estilos), **no garantiza tablas inline-style** que Gmail/Outlook prefieren. Puede introducir `style` no deseado, limpiar atributos necesarios.
- **Ventaja:** UX amigable para no-técnicos (no HTML).

**Veredicto B:** **Potente pero costoso y arriesgado para email** — preservación `{{...}}` incierta, estilos no deseados, doble UI lib.

### Opción C — Syncfusion Blazor RichTextEditor

**Fuente:** `https://blazor.syncfusion.com/documentation/rich-text-editor/getting-started` — `Syncfusion.Blazor.RichTextEditor`, `EditorMode.HTML` (default), `IFRAME/DIV`, markdown, toolbar customizable, `HTML view` para devs.

```razor
<SfRichTextEditor EditorMode="EditorMode.HTML" Placeholder="Type something">
```

- **WYSIWYG + source:** toolbar + `HTML view` (source directo). Soporta `IFRAME`/`DIV`, `placeholder` `.e-rte-placeholder` custom CSS.
- **Licencia:** **Comercial** — `SyncfusionLicenseProvider.RegisterLicense("YOUR LICENSE KEY")` en `Startup.cs`/`Program.cs`. Community si califica, sino pago (≈ $1k/dev). No MIT.
- **Blazor WASM:** soporta WASM y Server, modular `load on demand`.
- **Email HTML:** similar a Telerik — WYSIWYG genera HTML normalizado, toolbar puede introducir estilos, pero `EditorMode.HTML` ayuda. `Quick toolbar`, tablas, imágenes, links soportados. `Placeholder` `{{...}}` mismo riesgo de transformación que Telerik si no se usa `HTML view`.
- **Syncfusion vs Telerik:** Syncfusion 16k snippets, benchmark 70.26, High rep; MIT no, vendor lock sí.

**Veredicto C:** Similar a B — WYSIWYG profesional, pero **licencia + transformación HTML** no ideal para templates transaccionales con `{{...}}`.

### Opción D — Solución propia ligera (Source + Preview + Toolbar mínima)

**Concepto:** `textarea` mejorada o `contenteditable` + `iframe sandbox` preview + toolbar: `[HTML] [Preview] [Formatear] [Validar]`, buscar `{{...}}`, validar placeholders, expandir editor, sin framework UI completo.

- **Tecnología:** JS existente (CodeMirror 6, Prism, o Monaco ligero sin BlazorMonaco wrapper) + `iframe sandbox="allow-same-origin"` para preview.
- **Licencia:** MIT (si CodeMirror/Prism).
- **Ventaja:** bundle mínimo, sin Telerik/Syncfusion/MudBlazor clash, control total `{{...}}`, toolbar exacta para PassPlat (Formatear HTML via `prettier`/`js-beautify`, Validar placeholders via `Fluid` parse, Buscar).
- **Con:** construir y mantener editor propio (syntax highlight, folding, minimap) cuesta más que consumir `BlazorMonaco` ya empaquetado para .NET 10. Duplica esfuerzo si Monaco ya resuelve.

## Security Analysis (G6)

**Preview actual (`HtmlPreviewDialog.razor`):**
```razor
@((MarkupString)ContentText)
```
- **XSS:** `ContentText = CuerpoHtml` (arbitrario, no sanitizado en `EmailTemplateService`) renderizado **en mismo DOM** que app. Si `CuerpoHtml` contiene `<script>alert(1)</script>`, `onclick="..."`, `javascript:`, `iframe`, `embed`, `img onerror`, se ejecuta en contexto de `https://localhost:7275` (cookies, `AuthService`, `Navigation`).
- **HTML arbitrario:** `HasMaxLength(-1)` permite cualquier HTML, sin `HtmlSanitizer`, sin denegar `script/event handlers`.
- **Imágenes externas:** `<img src="https://attacker.com/pixel">` carga pixel tracking en preview.
- **Sandbox:** **No existe** — `MudPaper` no es `iframe sandbox`.

**Recomendación segura para S46.1 Design:**
- Preview en **`iframe sandbox="allow-same-origin"`** o `srcdoc` con documento aislado: `<iframe sandbox="" srcdoc="@HtmlContent">`.
- CSP `default-src 'none'; style-src 'unsafe-inline'` (email requiere inline).
- Eliminar `script`, `on*`, `javascript:`, `iframe`/`embed`/`object` antes de preview (allowlist `table/tr/td/div/h1-h6/p/a/img/link/style`).
- Tratar HTML como **contenido no confiable**, no navegación desde preview.

**G6 veredicto:** `HtmlPreviewDialog` es **SEGURIDAD P2** (XSS preview) aunque no afecta envío (MailKit/Gmail sandboxea). No es P0 porque preview solo la ve operador con `EMAIL_TEMPLATES_VER`, pero debe corregirse en S46.1.

**Pipeline envío seguro (no modificar):** `PassPlatEmailService` → `Fluid` (Liquid) → `MailKit` → SMTP Gmail — Fluid escapa por defecto, MailKit no ejecuta scripts, Gmail sandboxea. El riesgo es solo preview local.

**Título:** `EmailTemplates — HTML Source + Preview Seguro + Validación Placeholders`
